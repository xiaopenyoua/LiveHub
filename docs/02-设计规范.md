# LiveHub 设计规范

> 版本 v1.0 · 2026-10-29
> 适用：Android TV 1920×1080（按 4K 等比放大）
> 设计语言：参考 Apple tvOS —— 真黑底、内容优先、焦点驱动、极简控件

---

## 一、核心概念：没有台号，只有房间号

早期版本虚构过一套「跨平台三位台号」：哔哩 1xx、斗鱼 2xx、虎牙 3xx、抖音 4xx，数字键三位直达。**这套东西在 2026-10-29 被推翻了**——直播没有台号这个说法，四个平台的编号体系彼此不兼容，也从来没有一家做过跨平台统一编号。虚构编号不只是「不准确」，它会连带污染搜索（要造「台号匹配」的排名）、换台（要拿编号当大字）、分类（要造号段菜单）三个地方。

**四个平台真实的房间标识**

| 平台 | 叫什么 | 形态 | 说明 |
| --- | --- | --- | --- |
| 斗鱼 | 房间号 | 纯数字，4–8 位 | 网址末尾那串就是。大主播有 4 位短号（`9999`），普通主播 7–8 位。房间号唯一，输房间号是最精准的找法 |
| 虎牙 | 房间号 | 纯数字，最多 8 位 | 2018-04-12 起系统随机发放、不可自选，与 YY 号、频道号无关。官方：「用户通过房间号搜索，默认会优先展示该房间号对应的直播间」 |
| 哔哩哔哩 | 两套 | 短号（可无）+ 8–10 位真实房间号 | 主播自选 `short_id`，没有时为 `0`；系统分配 `room_id`。地址栏显示短号，但大部分接口只认真实房间号，需 `room_init` 转换 |
| 抖音 | 无房间号 | 抖音号：自定义字符串 | `live.douyin.com/<数字>` 那串是内部 room id，不给用户记。用户记的是抖音号。直播伴侣里的「直播间 ID」每次开播都会变 |

**数据模型**

一条直播只存它自己平台那套，不转换、不映射、不排名：

```js
{ rid:'660000', kind:'room', p:'huya', ... }   // 虎牙房间号
{ rid:'xiaojiuguan', kind:'dyid', p:'dy', ... } // 抖音号
```

- `rid` 是字符串，比对一律 `r.rid === String(input)`，**永远不 `Number()`**。转数字会把「抖音号是字母」和「房间号前导零」两种台账直接打乱。
- `kind` 决定界面写「房间号」还是「抖音号」。抖音没有房间号，硬写三个字就是错的。
- 凡界面上露出来的字符，都必须是屏上键盘打得出来的。抖音号允许下划线，数据里就避开了——没有下划线键，带了等于藏起来。
- 换台顺序按数组的编辑顺序，不按编号排序：房间号长度不一，还混着字母串，排序没有意义。

**因此删掉的东西**

| 删掉的 | 原因 |
| --- | --- |
| 卡片左上角的三位台号 | 改为**平台名**。8 位数字塞不进药丸，一排卡片立刻参差；而聚合客户端里这一格最该回答「这是哪个平台的」 |
| 换台条 120px 大字台号 | 改为**主播名**。6–10 位数字 120px 一行放不下；换台时人想确认的是「下一台是谁」 |
| 分类左栏号段（100–199…） | 改为**该平台在播数量**。对比「哪家内容多」比对比不存在的编号有用 |
| 数字键三位直达 | 真实房间号 4–10 位、抖音号是字母串，遥控器数字键没有回显，盲打错一位就跳错台且无声无息。找台走搜索 |
| 搜索的「123 / ABC」模式切换 | 见第八章。数字和字母同一块键盘，没有第二种搜索方式 |

**替代方案是什么**：搜索。输入框看得见、边打边筛、按「完全相等 > 前缀 > 包含」排序。直播间标识不再是导航手段，而是校验手段——「我搜到的这个是不是刚才那个台」。

## 二、色彩

真黑底，靠明度分层，颜色只出现在两处：**在播红**与**封面图本身**。

```css
--ground:   #000000;  /* 全局底色，导航与内容同一层 */
--panel:    #121214;  /* 卡片图未加载时的底 */
--raised:   #1C1C1F;  /* 面板、输入框、OSD */
--raised-2: #2A2A2E;  /* 面板内的嵌套块、进度条底 */
--text:     #FFFFFF;  /* 主文本 */
--muted:    #B4B4B4;  /* 次要文本、未选中标签 */
--faint:    #8E8E93;  /* 元信息、时间、人数 */
--live:     #FF453A;  /* 唯一强调色：在播、进度、主按钮 */
```

**用色规则**

- 强调色只出现在：LIVE 圆点、直播进度条、"进入直播间"主按钮。**不用于标题、标签、导航、图表。**
- **不使用四家平台的品牌色。** 平台用两个汉字表示（哔哩 / 斗鱼 / 虎牙 / 抖音），写在卡片左上角的药丸里。四个品牌色放在一起会让界面失去焦点，在 3 米外也分辨不出来。
- 卡片之间用明度差分隔，**不用 1px 描边**——1080p 上的 1px 线在沙发上等于不存在，只会变成脏点。
- 不使用毛玻璃、发光、彩色投影。TV 芯片做实时模糊会掉帧。

**对比度**：正文 `#FFF` on `#000` = 21:1；次要 `#B4B4B4` on `#000` = 11.1:1；元信息 `#8E8E93` on `#000` = 6.4:1。均高于 WCAG AA。

## 三、字体

```
拉丁与数字  Inter（自托管，assets/fonts/InterVariable.woff2）
中文        -apple-system → "PingFang SC" → "Microsoft YaHei" → sans-serif
```

两段式字族：拉丁与数字用 Inter，中文落回系统黑体。这么做的理由有三个——房间号、人数、时长全部是数字，Inter 的等宽数字（tabular）在小数点对齐上比系统字干净；Inter 与 SF Pro 的比例接近，换成 Apple TV 真机时观感不会跳；自托管保证设计稿在任何机器上截出来的图一致。

单一视觉语气，靠字重与字号分层。**最小字重 400，禁用细体**——TV 上的细体在压缩后会消失。

| 令牌 | 字号 | 字重 | 行高 | 用途 |
| --- | --- | --- | --- | --- |
| `--fs-hero` | 76px | 600 | 1.06 | 首页主图标题（最多 2 行） |
| `--fs-display` | 120px | 600 | 1 | 播放页主播名（换台条大字曾用这一档） |
| `--fs-h1` | 44px | 600 | 1.15 | 界面标题（分类 / 关注 / 搜索 / 设置） |
| `--fs-h2` | 34px | 600 | 1.2 | 内容行标题 |
| `--fs-title` | 26px | 600 | 1.3 | 卡片标题 |
| `--fs-body` | 24px | 400 | 1.5 | 正文、说明 |
| `--fs-meta` | 22px | 400 | 1.4 | 人数、时长、房间号 |
| `--fs-tab` | 30px | 500 | 1 | 顶部标签 |
| `--fs-card-meta` | 18px | 400 | 1.4 | 卡片副文本（平台 · 主播 · 人数） |
| `--fs-small` | 20px | 400 | 1.5 | 左栏副标题、说明行、设置项描述、弹层正文 |

字距：大字号 `-0.02em`，正文 `0`。数字一律 `font-variant-numeric: tabular-nums`，房间号和人数滚动时不抖动。

**两条硬规则。**

**一、字号下限 22px**（≈tvOS 29pt）。低于这个数在 3 米外读不出来，一律不用。

**二、相邻两档至少差 2px。** 档位多不是问题——Apple 自己的文字 ramp 就有 11 级；问题是"相邻两档只差 1px"，那不是层级，是噪声：用户分辨不出，维护时也无从选择。曾经散着 19/20/21/23/28/36/38 七个脱离令牌的硬编码值，其中 21 与 22 只差 1px、36 与 38 只差 2px 却分工不明。现在全部并入令牌，每屏实际落在 6–8 档、相邻最小间距 2px。

三个例外，都只用在"不承担阅读任务"的位置：

| 例外 | 字号 | 为什么不占 22px 的名额 |
| --- | --- | --- |
| 换台角标、LIVE 标记、弹层正文 | 20px | 贴在封面上的标记，靠颜色和位置被看见，不靠读 |
| 卡片副文本 | 18px | 卡片内的第三层信息，看一眼知道是哪家、多少人即可 |

卡片副文本为什么比页面其它 meta 更低一档：26px 标题配 22px 副文本只差 4px，三米外这两层会糊成一片，读不出主次。退到 18px 拉出 1.44 倍，层级才成立。卡片是信息密度最高的地方，副文本本来就该比别处更弱。

## 四、栅格与间距

```
画布        1920 × 1080
安全区      四边内缩 60px
内容边距    左右 80px（与安全区叠加后视觉留白 80px）
顶部导航    高 116px，底部与主图间距 32px
内容行间距  56px（行与行之间，明显大于行内 14px）
卡片间距    24px
```

- **一对等宽外边距**，左右都是 80px，任何界面不破例。
- 行间距（56）必须明显大于块内间距（14/24），否则大屏上会糊成一片。
- 纵向内容超出时整屏纵向滚动，焦点下移自动滚动；下一行的顶部**必须露出至少 24px**，作为"下面还有"的提示（不使用滚动条，3 米外看不见）。

## 五、圆角与控件

| 元素 | 圆角 |
| --- | --- |
| 封面卡 / 面板 | 20px |
| 头像 | 圆形 |
| 按钮 / 标签 / 开关 | 全圆（999px） |
| 输入框 | 20px |

**按钮只有两种**

1. **主按钮**：白玻璃胶囊，"进入直播间"。全屏最多一个。
2. **次按钮**：半透明玻璃胶囊，白字。

不用第三种。不做描边按钮——描边在大屏上过细。

### 5.1 按钮是玻璃，不是色块

这一条最容易做错。把按钮画成一块纯色（`#fff` / `--raised`）会立刻显得像网页控件，因为真实世界里没有一块完全均匀、边界锐利、颜色恒定的白色塑料。

tvOS 26 的按钮是 **Liquid Glass**：半透明材质，会吸收并模糊背后的内容，表面带一道**镜面高光**（specular highlight）。Apple 官方对 `CustomHoverEffect.highlight` 的描述是"投影效果配一道镜面高光，并随运动调整高光偏移"。所以：

| 层次 | 做法 | 作用 |
| --- | --- | --- |
| 底色 | 半透明白 + `backdrop-filter: blur(24px) saturate(180%)` | 颜色由环境决定：压在封面上会带封面的色，压在黑底上偏灰 |
| 顶沿 | `inset 0 2px 0 rgba(255,255,255,.98)` | 一道镜面高光，是"玻璃有厚度"的来源 |
| 底部 | `inset 0 -16px 24px -10px rgba(0,0,0,.24)` | 大范围柔暗，自上而下由纯白转微灰——**这就是"渐变"** |
| 底沿 | `inset 0 -3px 5px -3px rgba(0,0,0,.22)` | 收一道窄暗边，玻璃的边缘 |

**为什么用 `inset` 光而不是 `linear-gradient`**：渐变是画上去的颜色，无法过渡，焦点切换时会硬切；`box-shadow` 可以随时间插值，高光才能跟着动。而且真玻璃的高光是**光**，不是色带。

实测白色主按钮：顶部行平均亮度 **246**，底部 **229**，差 17 级——看得见但不会脏。纯色按钮这一差值是 0。

**不做外投影**：真黑底上外投影落进黑色等于没有，加了只是让代码"看起来像 Apple"。浮起交给 scale，实体感交给上面那层光。

## 六、焦点（最重要的一节）

在电视上，焦点就是光标。焦点错了，整个产品就废了。

### 6.1 焦点样式

**不放边框。** tvOS 的焦点不画环，靠"这块内容被举起来了"来表达：变大、变亮、底色抬一档。加环会把界面切成一格一格的表格，也违背"内容优先"。

| 属性 | 未聚焦 | 聚焦 |
| --- | --- | --- |
| 缩放 | 1.00 | **1.08**（封面卡）/ **1.06**（按钮、按键）/ **1.02**（列表项） |
| 边框 / 外环 | 无 | **仍然无**（不许出现描边） |
| 封面亮度 | 0.86 | **1.00** |
| 标题色 | `--muted` | `--text` |
| 表面 | 半透明玻璃（`--spec`） | 高光提亮（`--spec-on`）+ 底色抬一档 |
| 外投影 | 无 | **仍然无**（真黑底上投影不可见，只会脏） |

> 为什么不用投影：tvOS 在模糊壁纸上靠投影表现"浮起"，而我们是纯黑底，投影落进黑色里等于没有。所以"浮起"交给 **scale**，"选中"交给 **底色明度 + 高光亮度**。三米外靠尺寸差就能认出来，这是电视上最稳的焦点信号。
>
> 为什么不用白环：白环是键盘焦点（focus-visible）的语言，不是电视的语言。它会让每个卡片看起来像一个格子，压过封面本身。

**真正需要边界的场合只有一种**：焦点落在白色元素上（主按钮、白色按键）。此时不给描边，改用**反色填充**——聚焦后按钮仍是白色、文字仍是黑色，但整块放大；若所在背景也是白的，则把底色压到 `--raised-2` 再把文字转白。

> 注意：这里说的"玻璃"是 `inset` 内阴影，不是外投影。它为按钮提供高光与厚度，不改变"元素不浮起"的结论。

### 6.1.1 顶栏胶囊跟着焦点滑

顶栏的五个页签**不是各画一块底**——那会让屏幕同时亮起五个"选中项"，正是 tvOS 最忌讳的事。正确做法是**一层玻璃胶囊跟着焦点移动**：

- 胶囊是 `.tabs` 内的绝对定位元素，位置由 `offsetLeft / offsetWidth` 算出（不用 `getBoundingClientRect`，后者读到的是过渡中的中间值，胶囊会追着跑偏）。
- 焦点进入顶栏 → 胶囊淡入并滑到该页签下；焦点离开 → 淡出。
- 换屏时传 `instant`，新屏的胶囊直接出现在正确位置，不从上一屏滑过来。

顺带解决了原本最弱的一处焦点目标：页签从 `padding:10px 2px`（约 50px 高）变成 `11px 24px` + 胶囊，可点区域和视觉重量都到了按钮的量级。

### 6.2 焦点规则

1. **每屏必须有默认焦点**，且是用户最可能想要的那个（首页 = 主图主按钮，分类 = 第一张卡，设置 = 第一组）。
2. **离开再回来，焦点回到原处**，不重置。
3. **焦点不可困住**：任何位置按任意方向键都要有去处，没有去处就交给上一级。
4. **焦点移动必须空间可预测**：右就是右，绝不跳过中间元素。
5. 焦点移动只做 `transform` / `background-color` / `color` / `box-shadow`，时长 **200ms**，缓动 `cubic-bezier(.32,.72,0,1)`。这四个属性必须写在同一条 `transition` 里——漏掉 `box-shadow` 就会出现"块变大了、高光没跟上"的两半不同步。
6. **放大要有余量**：卡片放大 1.08 会向外顶出约 8% 尺寸，所以卡片网格的行间距必须 ≥ 36px、分组标题下沿距网格 ≥ 34px，否则聚焦的卡会啃到标题。

### 6.3 遥控器键位

| 键 | 全局 | 播放页（控制条隐藏） | 播放页（控制条显示） | 换台条打开 |
| --- | --- | --- | --- | --- |
| ↑ / ↓ | 上下移动焦点 | **换台**（上/下一台） | 切换按钮行 | 上/下一台 |
| ← / → | 左右移动焦点 | **换平台**（该平台第一条） | 切换按钮 | 换平台 |
| OK | 确认 | 显示控制条 | 执行 | 确认并关闭 |
| 返回 | 上一级（最高级回首页，不退出） | 回首页 | 隐藏控制条 | 关闭换台条 |
| 数字 0–9 | 无（首页 / 播放页不响应数字键） | 输入数字，与字母同键 | — | — |
| 菜单 | 打开设置 | 更多（清晰度/线路） | — | — |

**返回键规则**：最高级页面按返回，先回首页；首页再按返回，弹二次确认"退出 LiveHub？"。**永远不直接退出 App**——这是电视端最常见的挫败。

### 6.4 四向键的落点怎么算

这条得写进交接文档，否则开发会自己发明一套，然后"按右跳到奇怪的地方"这类问题会反复回来。

**不能按中心点距离排序。** 设置页从左侧导航按右，顶栏「首页」的水平中心只差 37px，而右侧第一行设置差 904px——它就近了，焦点窜到顶栏去。窄而长的元素在中心点距离上永远占便宜。

正确的算法分两步：

| 步骤 | 判据 | 作用 |
| --- | --- | --- |
| 筛方向 | 候选的**中心**必须在按键那一侧（> 4px） | 防止走到背后去 |
| 排序 | 按**边缘间隙**，哪一个真分开了就按分开多远排；副轴间隙 ×3 | 防止跨区抢焦点 |

**方向判据不能也用间隙**：首页第一次按右，301 那张卡的左边缘比"进入直播间"按钮的左边缘还靠左，间隙是负的，可它明明是这一行最该去的地方。中心差能过，间隙不能。两条判据各管一件事。

**副轴权重 3 是量出来的**，不是拍的：设置页那组候选里，顶栏 tab 的副轴间隙 225px、右侧设置行 0，权重低于 3.2 时 tab 会赢。

验收标准：全量跑一遍，五个屏 125 个可聚焦元素 × 4 方向 = 500 次，"不在边界却按不动"必须为 0。当前 0。

## 七、动效

**所有时间参数的来源**：tvOS 内置的 focus hover 是 **~200ms 的透视抬升 + 一道镜面光泽**。这是平台给的基准，不要自创更快的手感——比系统快会让界面显得神经质，比系统慢会让遥控器发黏。

| 场景 | 参数 |
| --- | --- |
| 焦点移动 | **200ms**，`cubic-bezier(.32,.72,0,1)` |
| 按压回弹 | **120ms**，`scale(.96)`（必须比焦点快，否则按下去像没反应） |
| 顶栏胶囊滑动 | 260ms（它要走一段距离，需要比单点缩放久一点才不跳） |
| 界面切换 | 交叉淡入 240ms + 缩放 0.985 → 1 |
| 换台条弹出 | 从底部 60px 上浮 + 淡入，280ms |
| 封面加载 | 淡入 200ms，`--panel` 打底，禁止骨架屏闪光 |
| 弹幕 | 24s 横穿，右上到左，线性 |
| **开关位移** | **180ms**，`cubic-bezier(.4,0,.2,1)` |
| **开关变色** | **120ms**，延后 **55ms**，`--ease` |

一条过渡覆盖四个属性：

```css
--t-surface:transform var(--dur) var(--ease),
            background-color var(--dur) var(--ease),
            color var(--dur) var(--ease),
            box-shadow var(--dur) var(--ease);
```

- 只动 `transform` / `background-color` / `color` / `box-shadow`，不动 `width` / `top` / `left`（会触发布局）。
- **按压态必须与焦点态用同一条过渡**，只把时长压短。分开写会出现"先跳再动"。
- `prefers-reduced-motion` 降级：把 `--dur` / `--dur-press` / `--dur-sw` / `--dur-sw-color` 压到 1ms、`--sw-delay` 归零，**不删 transform**——本项目没有边框，缩放是唯一的焦点线索，状态必须到达、过程才去掉。
- **任何内容都不许依赖动画才出现**——脚本失败时内容必须已经在那里。

### 7.1 为什么"按钮切换"必须有动画

遥控器没有触感反馈，也没有鼠标悬停。用户按一下，唯一的确认就是**眼前那块东西变了**。如果状态是瞬跳的，大脑读到的是"闪了一下"，而不是"我移动了焦点"。动画在这里不是装饰，是**因果关系的表达**：先有按键，后有变化，中间那 200ms 就是"听到了"。

反过来，动画也不能长到让人等待。200ms 是 Apple 在电视上验证过的数字：短到感觉即时，长到能被看见。

### 7.2 开关不能借焦点曲线

**焦点和开关是两种运动。** 焦点是"一块面被举起来"，面可以极快起步，没有位移；开关是"一个点滑过去"，点的起步必须能被看见。把焦点那条 `.32,.72,0,1` 直接套到滑块上，结果是"冲一下然后卡住"。

这不是感觉，是采样出来的。每 20ms 读一次 `::after` 的 `DOMMatrixReadOnly(...).m41`：

| 时刻 | 位移 | 占比 |
| --- | --- | --- |
| 22ms | 9.2px | 24% |
| **86ms** | **31.7px** | **83%** |
| 235ms | 38.0px | 100% |

前 86ms 冲掉五分之四，剩下的 150ms 只挪 6px。曲线没问题，是**用错了地方**：它的起点加速度是为"面被托起"设计的，给一个 38px 的位移用，就变成一记弹射。

过冲曲线 `.34,1.4,.64,1` 更糟：64ms 就走完 80%，滑块早早到站，轨道怎么调都追不上，看上去是滑块先飞过去、轨道在后面慢慢亮。

最终定案：

```css
--dur-sw:180ms;                      /* 位移 */
--dur-sw-color:120ms;                /* 滑块变色 */
--sw-delay:55ms;                     /* 等位移走过大半再翻色 */
--sw-ease:cubic-bezier(.4,0,.2,1);   /* Material standard，位移与轨道共用 */
```

改完的采样，每 20ms 推进 **0.8 / 10.9 / 9.2 / 6.6 / 7.1 / 1.7 / 1.1 / 0.5**——一段连续滑行，末端 3.4px 摊在 72ms 里，读作"靠住"不是"拖住"。

三条约束：

- **变速和动位移不能同起同止。** 两者同时跑，中途那一帧是"灰滑块 + 半亮轨道"，对比度最低，眼睛只接住一次闪。延后 55ms：先看见它滑过去，再看见颜色反过来。
- **颜色曲线不能过冲。** 位移可以，alpha 不行——顶到 1 就提前饱和，后面的时间等于白等。
- **轨道必须和滑块同一条曲线。** 它们是一个东西在动；轨道自己用更快的曲线就会抢在滑块前面亮一下。

> 采样方法：CDP 每 20ms 读 `getComputedStyle(el,'::after')`，`DOMMatrixReadOnly` 的 `m41` 给位移，`backgroundColor` 给颜色。主观的"不流畅"必须先翻译成数字，否则每一轮修改都只是换一条没验证过的曲线。

## 八、界面信息架构

```
首页（只做热门推荐，不放个人内容）
├─ 主图（正在播的最大热点，1 个）
└─ 正在直播（全平台混排，按热度，4 列网格，整页可向下滚）

关注
├─ 正在直播（卡片网格，一行 4 列）
└─ 未开播（同款网格，封面压暗 0.5，保留平台名）

分类
├─ 左：平台（全部平台 / 哔哩哔哩 / 斗鱼 / 虎牙 / 抖音，各带在播数量）
└─ 右：分类标签 + 16:9 网格（4 列）

搜索
├─ 左：一块键盘（数字行 + 三行 QWERTY + 删除/清空/搜索），上面是输入框
└─ 右：实时结果 + 最近搜索（结果是卡片网格，3 列）

播放
├─ 视频 + 弹幕
├─ 顶部信息条（平台 / 主播 / 房间号 / 标题 / 人气 / 画质）
└─ 底部控制条（弹幕 / 清晰度 / 线路 / 换台 / ＋ 关注）

换台条（播放页 ↑↓ 呼出）
└─ 大号主播名 + 预览图 + 标题 + 平台·房间号 + 人数

设置
├─ 播放（解码 / 画质 / 线路策略 / 缓冲）
├─ 弹幕（字号 / 速度 / 密度 / 屏蔽）
├─ 账号与同步（扫码 / 同步码）
└─ 关于（版本 / 内容来源 / 开源许可）
```

**首页为什么去掉"关注的主播"和"平台索引"**：首页只回答"现在有什么好看"。把关注塞进首页，会让推荐流被个人订阅切碎；把平台入口塞进首页，会把"换台"这件动作变成"先看表再按键"。两件事各自有归宿——关注去关注页，平台去分类页。首页保持纯粹的推荐流，是这一版最重要的取舍。

**卡片网格为什么是 3–4 列而不是 5 列以上**：三米观看距离下，卡片宽度低于 400px 时封面里的人脸就糊了，标题也只能塞下 8 个字。一行 4 列是"能认出是谁"的下限；再密就退化成缩略图墙。搜索页因为右栏被键盘让走了 830px，只能用 2–3 列。

**首页的热门推荐为什么不再横滑**：横滑一次只能看见四张，而且"还有更多"这个信息藏在屏幕外，遥控器上下键的直觉是"往下还有"。改成和关注页同一套竖排网格，一屏看见八张，往下滚就是翻页。横滑只适合"每项都很宽"的封面流，这里的卡片本来就不宽。

**每个界面只回答一个问题**：首页"现在有什么好看"、关注"谁在播"、分类"某平台某分类有什么"、搜索"那个主播在哪"、播放"看得爽不爽"、设置"怎么调成我要的样子"。

### 8.1 设置页：一行就是一块玻璃

设置页左右两栏**必须用同一套焦点语言**。这是最容易做错的地方：左栏做完玻璃胶囊，右栏却只把底色换成 `--raised`，屏幕就会同时出现两种焦点风格，右侧看着像网页的 hover。

| | 左栏分组 | 右侧设置行 |
| --- | --- | --- |
| 底色 | `rgba(255,255,255,.13)` | **同左** |
| 缩放 | 1.02 | **同左** |
| 高光 | `--spec` | **同左** |
| 时长 / 曲线 | 200ms / `cubic-bezier(.32,.72,0,1)` | **同左** |
| 圆角 | 16px | **同左** |
| 说明文字 | — | 焦点时 `--faint` → `--muted` |

行内的控件也必须是玻璃，不能一半玻璃一半纯色：

- **分段控件**：轨道是 `rgba(255,255,255,.08)` + `--spec-chip`；选中项由一枚**滑动的白色药丸**表示（260ms），而不是给某个 `<b>` 加底色——加底色就是硬切，眼睛接不住切换。
- **开关**：关态轨道是 `rgba(255,255,255,.13)` 玻璃，开态转白；滑块 180ms 滑过去，变色延后 55ms（见 7.2）。

**默认焦点落在第一项设置上**，不是左栏。理由：进设置页是想改设置，不是改分类。

> 药丸定位的两个坑：一是用 `offsetLeft / offsetWidth`，`getBoundingClientRect` 会在面板重渲染那一帧读到布局前的值；二是 `getComputedStyle` 返回的是**实时对象**，想比较前后两个状态必须立刻把值抄成字符串，否则两次读的是同一个对象。

### 8.2 滚动：谁滚、谁不动

五个屏分两类，没有第三种：

| 类型 | 屏 | 行为 |
| --- | --- | --- |
| 单栏 | 首页、关注 | 整页一个滚动容器 |
| 分栏 | 分类、设置、搜索 | 左栏钉死，**只有右栏滚** |

判断依据不是屏幕尺寸，是**左栏承担什么职责**。分栏页的左栏是"我在哪"的坐标系（平台与在播数量 / 设置分组 / 输入键盘），跟着内容滚走，用户滚到第二屏就不知道自己站在哪了。单栏页没有这个坐标，标题跟着走没有损失。

实现只有一行是命门：

```css
.browse{flex:1 1 auto; min-height:0; display:flex}
```

**`min-height:0` 不能省。** flex 子项默认 `min-height:auto`，意思是"我不能比内容更矮"。于是内部那个 `overflow-y:auto` 的容器会被内容顶开，高度永远等于内容高度，滚动条永远不出现，整页跟着一起滚——这是"我明明写了 `overflow:auto` 却不滚"的唯一原因。

设置页的面板多两行：

```css
.panel{align-self:flex-start; max-height:100%; overflow-y:auto}
```

两个缺一个都不对：

- 只留 `align-self:flex-start`：内容少时是一张内容高的卡片（对），内容超长时溢出到屏幕外（错）。
- 只留 `max-height:100%`：每张面板都被撑满整列，内容少的组下半截空着，像一块没做完的白板。

还有一条容易忘的连带责任：**面板变成自己滚之后，换分组必须手动 `scrollTop = 0`**。上一层滚到一半切过来，新分组会从一个莫名其妙的位置开始。

**"能滚"要有量，不能只有声明。** 设置页原先是 15 项，加起来正好 773px，等于可视高度——`overflow:auto` 写了，但一条都不需要滚，这个特性等于不存在。扩到 23 项后才真的可滚 103px。凡是"支持滚动"的需求，都要量 `scrollHeight > clientHeight`。

焦点移到视口外会自动带动最近的滚动祖先，不用写代码：`setFocus` 到最后一张分类卡，右栏自己滚到 940px，卡片落在 y=809–1080 完整可见。

**播放页的顺序为什么是 `弹幕 → 清晰度 → 线路 → 换台 → ＋ 关注`**：前四个都是"看这一次"的参数，关注是"以后都看"的动作。它不在这条参数链上，它是出口，所以放末尾。主按钮属性（白底黑字）顺带把它和四个玻璃胶囊分开——不需要额外加分隔线。

### 8.3 搜索：一块键盘，一种输入

**上一版做错了什么**：键盘分「字母 / 数字」两个模式，中间放一枚 `123` 切换键，输入框左上角再挂一枚「数字」徽标。要搜「小鹿233」，得按 `123`、打三位数字、再按 `ABC` 切回来。

这个设计的病根不在交互，在**前提**：它假定"数字"是另一种搜索任务（查台号），所以要一个独立模式。而台号不存在（见第一章），"我现在要输入数字"这件事本身就不该发生。

**现在的做法**：只有一块键盘。

```
┌──────────────────────────────────────────────┐
│ 输入框（96px，等宽数字，占位提示里写清能搜什么）        │
├──────────────────────────────────────────────┤
│ 1 2 3 4 5 6 7 8 9 0        ← 数字行，十列满铺，与字母同尺寸 │
│ Q W E R T Y U I O P
│  A S D F G H J K L         ← 短行错位：缩半键
│   Z X C V B N M            ← 短行错位：缩一键半
│ [ 删除 ] [ 清空 ] [  搜索  ]  ← 跨度 3+3+4 凑满十列
└──────────────────────────────────────────────┘
```

- **数字行在最上面、和字母同宽同高。** 不是"另一个模式"，是同一块键盘的一行，像实体键盘那样。上一版数字键是 155×145 的大键，因为那时数字只用来打台号；现在数字是自由输入的一部分（房间号 4–10 位、抖音号里也有数字），和字母同等地位，也就不该有不同的尺寸。
- **键高一律 92px，加一行不改任何一枚键的手感。** 五排：5×92 + 4×14 = 516。键盘拿到的高度预算是 621（809 − 32 上边距 − 96 输入框 − 28 间距），516 之后余 105，键盘不下沉、底边留白。
- **工具行从 2+2+2+4 变 3+3+4。** 空出来的那一列是原来的模式键位置，平均分给两个工具键；搜索键仍是最宽的 4 列——它是这一屏唯一的下一步。
- **不做"字母/数字"混输的语法限制。** 只挡输入框容量（12 位），不挡内容。任何"第几位之后不许输入"的规则都会误伤房间号或抖音号。

**匹配规则（`searchHits`）**

只按"匹配得有多准"分三档，**没有字段权重**：

| 档 | 条件 | 说明 |
| --- | --- | --- |
| 0 完全相等 | 主播名 / 房间号 / 抖音号 / 拼音 / 标题 | 唯一指向一个直播间，结果区给一句「按「搜索」直达」 |
| 1 前缀 | 房间号 / 拼音 / 主播名 | 从头开始打是这类输入的习惯，比"包含"更可信 |
| 2 包含 | 主播名 / 标题 / 房间号 / 分类 | 分类命中的是一类、不是一个直播间，所以固定落最后一档——"游戏"不该排在任何具体直播间前面 |

上一版有「台号 > 主播名 > 标题 > 分类」这条业务权重。台号不存在，权重也就不该存在：权重是在补偿一个虚构字段的精度优势。

- `rid` 一律当字符串比，**永远不 `Number()`**。哔哩 8–10 位、斗鱼 4–8 位、抖音号是"字母+数字"，转成数字会把台账打乱。
- 直达提示的判据是"排第一的那条 `rank === 0`"，**不是"输入了几位数字"**。任何按位数写死的条件都会把 `9999`（斗鱼短号）和 `xiaojiuguan`（抖音号）挡在门外。
- 「搜索键打开第一条」和「直达提示」共用同一个 `hits[0]`，两者不可能不一致。
- 空查询不显示结果，最近搜索顶上来当主角。上一版固定摆四张卡，等于说"什么都没输也有结果"。
- 最近搜索存的是**你打过的那串字**（`660000` / `lpe` / `xiaojiuguan`），点一下填回输入框；不是四条直播间。

**已知取舍**：屏上键盘只能产出 ASCII，所以中文主播名、中文标题、中文分类这三条匹配分支从键盘这条路走不到——它们留给系统输入法与语音搜索。占位提示因此写的是"拼音首字母、房间号或抖音号"，不承诺"输入中文也能搜"。匹配函数保留中文分支，是因为产品接上语音/输入法之后它就是对的；但界面文案不能替它吹牛。

## 九、播放页：画面永远是屏幕里最亮的东西

这一节是照 tvOS 26 的原话定的：「始終以內容為觀看體驗的核心」——快轉、睡眠計時器、調音量、控制中心這些场景，都保持影片置前、置中。

### 9.1 不调曝光，只压两条带

早先的做法是给视频挂 `filter:brightness(.78)`，控制条收起时挂 `.92`。等于用户看两小时直播，两小时都在看一张被调低曝光的画面。

量过才知道亏：对四张真实封面做条带亮度采样、再乘遮罩 alpha 算对比度，**这层压暗对顶栏文字的对比度只贡献 +0.4～+1.0（19.4 → 19.0 这种量级），代价是整幅画面亮度直接乘 0.78。**

现在：

```css
.player__video{ /* 不挂 filter */ }
.player__scrim{
  background:linear-gradient(180deg,
    rgba(0,0,0,.90) 0%, rgba(0,0,0,.74) 12%, rgba(0,0,0,.44) 20%, rgba(0,0,0,0) 36%,
    rgba(0,0,0,0) 55%, rgba(0,0,0,.58) 74%, rgba(0,0,0,.82) 88%, rgba(0,0,0,.94) 100%);
}
```

顶栏（y 5%–14%）与底栏（y 83%–95%）所覆盖的两条带子被压到 0.6–0.9，**36%–55% 的画面中段一点不碰**。

### 9.2 收起控制层，把整块屏幕还回去

`playerState === 'idle'` 时，遮罩一起 `opacity:0` 淡出，而不是"只把按钮藏起来、画面还蒙着一层"。

### 9.3 浮层文字要自己保证可读，不能要求画面让路

换台提示原用 `--faint`(#8E8E93)，落在最亮的那张封面（LED 墙）上实测只有 **2.55:1**。改成 `--muted`(#B4B4B4) 并把底栏那段遮罩加深后，最差一张 **4.74:1**。

这和弹幕用描边代替投影是同一条原则：**可读性是文字的責任。** 反过来做——为了让一行说明看得清而把整部片子压暗——是本末倒置。

### 9.4 控制层占多少画面

| 状态 | 顶栏 | 底栏 | 换台卡 | 占屏比 |
| --- | --- | --- | --- | --- |
| 控制条显示 | 96px | 124px | — | 20.4% |
| 换台条 | 96px | 124px | 237px | 48.2% |
| 收起 | — | — | — | 0% |

视频始终 1920×1080 满屏，**不因控制层出现而被推挤、缩放或改变构图**。

## 十、状态设计

| 状态 | 呈现 |
| --- | --- |
| 在播 | 红点 + "直播中" |
| 未开播 | 灰点 + "未开播 · 预计 20:00"，封面对比度降到 0.5 |
| 线路异常 | 卡右上角"线路异常"胶囊，点击直接进备用线路 |
| 已降级 | 播放页角落一行小字："已自动切到备用线路 · 720P" |
| 加载中 | `--panel` 纯色 + 平台名，不闪光、不骨架跳动 |
| 空（无关注） | 一句说明 + 一个动作："还没有关注的主播。在播放页按 OK 就能关注。" |
| 无网络 | 整屏说明 + "重试"按钮，不显示任何假卡片 |

**原则：宁可少一个卡片，也不显示一个点进去会黑的卡片。**

## 十一、弹幕（大屏专用参数）

## 十二、开发交接要点

1. 所有尺寸按 1920×1080 稿 1:1 标注，dp 换算 = px（Android TV density 通常 1.0 或 2.0，按 1080p 基准实现）。
2. 焦点用 Android 原生 `requestFocus` / `nextFocusDown` 等属性，**不要自定义焦点引擎**——系统焦点已经处理了空间寻址，自定义只会更难调。
3. 卡片统一 `CardView` + `focusable`，在 `OnFocusChangeListener` 里做缩放与环，用 `ViewPropertyAnimator`。
4. 图片加载用 Glide/Coil，占位色 `#121214`，禁止占位图。
5. 关注的直播间按 `rid` 持久化，跟账号走，跨端同步；`rid` 是各平台自己的号，不做转换。

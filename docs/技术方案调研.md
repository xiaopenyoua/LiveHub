# 技术方案调研：四平台直播 TV 客户端

> 日期：2026-10-30
> 范围：这个应用该用什么技术、为什么不用别的；两个参考实现里**能抄的**和**不能抄的**；本工程的长时段稳定性设计。

## 0. 一页结论

1. **播放内核：Media3 / ExoPlayer，不引第二套内核。** 参考 APK 塞了 6 套（Exo/系统/IJK/阿里/mpv/VLC），代价是 160 MB 包体与「换内核像换一个 App」；收益只是老盒子的兼容性兜底。LiveHub 的目标面是 Android TV 5.0+，Media3 的 FLV/HLS 解析与 MediaCodec 硬解已经覆盖；真遇到解不了的编码，错误分类会明确说「这台设备解不了」，而不是假装播放。
2. **长稳的关键不是内核数量，是「知道自己在不在播」。** 两个参考实现都缺真正的播放层看门狗：APK 只有起播 10s 一次性检查和 2s 错误防抖；DTV 连 error/stall 监听都没有。LiveHub 现在有：首帧判据、8s 停住看门狗、12s 无首帧兜底、EOF 重连、地址过期重取、错误换线、失败可见、手动重试。
3. **地址会过期，续流是直播的第一性需求。** DTV 用「斗鱼 300s 预取 + FLV tag 接续」证明这一点；LiveHub 的斗鱼预览地址 TTL 更短（实测约 60s 后分片 403），所以每次 EOF/403/连续加载错误都**重新取地址**再回到同一条线，而不是拿旧 URL 反复 `prepare()`。
4. **缓冲策略不能照抄参考实现的「零缓冲」。** APK 的 IJK 是 `fflags=nobuffer` / `packet-buffering=0`，mpv 还关 cache；那是低延迟取向。30 分钟场景要反过来：Media3 LoadControl 取「最小维持 5s / 最大 20s / 起播阈值 1.5s / 重缓冲后 3s」。
5. **错误归责是产品能力。** DTV 把取流异常一律说成「主播未开播」，APK 也把内核错误引导到「手动换播放器」。LiveHub 保留 13 个 `SiteError`，由 `retryable` 决定给「重试」还是「换线路 / 回首页」；这是不能妥协的一层。

### 1.1 它是什么（观测）

### 1.2 六个播放内核（观测 + 上游 1.7.4 对照）
| index | 标签 | 实现 | 关键参数 |
| --- | --- | --- | --- |
| 0 | Exo | `gsy_video_player` → Media3 | `SurfaceView`；`setTimeOut(4000)`；`cacheWithPlay=false` |
| 1 | 系统 | Android `MediaPlayer` | 同上封装 |
| 2 | IJK | `libijkplayer` + `libijkffmpeg` | **低延迟取向**：`probesize=200`、`packet-buffering=0`、`infbuf=1`、`framedrop=1`、`max_cached_duration=30`、`fflags=nobuffer`、`skip_loop_filter=48` |
| 3 | 阿里 | ApsaraVideoPlayer SaaS | SDK 默认；候选版本串 `5.5.6.0` |
| 4 | mpv | media_kit / libmpv（FFmpeg n6.0） | `vo=gpu`、`hwdec=auto-safe`、32 MiB 前向/后向缓冲；**Texture**，不是 SurfaceView |
| 5 | VLC（本 APK 增量） | `flutter_vlc_player` / LibVLC 3.0.19 | `:network-caching=1500`、`:http-reconnect`；Texture；单 ABI 39–50 MB |

**选核是手动的，没有自动内核降级**：`videoPlayerIndex` 默认 0；播不动时自动做的是「切线路」，换内核在设置页手选。**也没有硬解失败自动回退软解**。

### 1.4 稳定性机制与缺口

**有**：
- 播放错误（`GSY onError` / mpv `stream.error`）→ **2s 防抖** → 非最后线路就切线路；最后线路则刷新房间（「每 10 秒刷新直播间信息…」）。
- 起播后 **10s 一次性**检查：`!isPlaying` 且有网 → `refresh()`。
- 一个 **20s** 计时器，但只在「手动暂停 + 控件已隐藏」的窄条件下才可能命中——**不是通用卡顿看门狗**。
- 弹幕 WS：连接 10s、最多重连 5 次、每 5s 一次，**无指数退避/抖动**。

**缺口**（LiveHub 不能照抄）：
1. 没有位置/缓冲前进看门狗；CDN 保持连接但不吐流时会停在最后一帧。
2. 没有 EOF/onCompletion 的显式处理：直播被对端关闭时只更新 `isPlaying`，不会重新取流。
3. 没有 ABR；清晰度只在起播选一次。
4. 没有预取下一条线路/预热 DNS/TCP。
5. 切线路是 `destroy → 2s → 重建`，黑屏 2–5s 是设计内的。
6. 没有自动 hw→sw、没有自动换内核。
7. **弹幕实现不是「无上限 + 每条一个 AnimationController」**：REA 复核看到的是自研 `BarrageWall` + `TickerProviderStateMixin` 统一驱动，设置里有「弹幕数量 / 弹幕合并 / 弹幕区域」，并有 `danmu_merge.dart`。**消息队列是否封顶仍是未知**，高并发内存影响需要实测；不要把「上游旧版推断」写成 APK 观测。
8. 斗鱼签名走第三方**明文 HTTP**，是单点故障与隐私风险。

### 1.5 低端 TV 性能

- 渲染：Exo/系统/IJK/阿里走 **SurfaceView**（对低端 TV 好，少一次合成）；mpv/VLC 走 **Texture**（多一次拷贝）。
- 内存：manifest **没有 `largeHeap`**；`cached_network_image` 只限制 20 对象/1 天，但 Flutter 默认 `imageCache` 仍是 1000 张/100 MB；弹幕列表与动画无上限。
- 启动：`main()` 里 Supabase 初始化在首帧前；`pure_live_web`（1.7 MB `main.dart.js` + canvaskit）也打进 APK，对播放主路径不是必需。
- 权限：`MANAGE_EXTERNAL_STORAGE` + 旧存储权限过宽；`usesCleartextTraffic=true`；没有 `WAKE_LOCK`，常亮走 `FLAG_KEEP_SCREEN_ON`（正确）。

### 1.6 能抄 / 不能抄

| 能抄 | LiveHub 落地 |
| --- | --- |
| 起播失败 → 2s 防抖 → 换下一线路 → 全失败 → 刷新房间 | 起播 4s 起逐条换；错误 1.5s 后换；全部失败进终态 |
| 线路/清晰度切换不重建 UI，只换播放源 | `LivePlayer.play()` 复用 ExoPlayer，只 `setMediaSource` |
| SurfaceView + `KEEP_SCREEN_ON` | `PlayerView` 默认 SurfaceView；`keepScreenOn` |
| 多 CDN / 多清晰度候选 | 四家 `playUrls()` 返回已排序候选；虎牙 4 线、哔哩 6 线 |
| 斗鱼取流本地化 | LiveHub 用 `hlsH5Preview`（md5 本地算），代价是单档 + 短 TTL，必须重连续流 |

| 不能抄 | 原因 |
| --- | --- |
| 6 套内核全塞进 APK | 包体 160 MB；每套内核的缓冲/重连行为不同，测试矩阵爆炸 |
| 手动换内核作为兜底 | 用户不知道什么时候该换；错误弹窗让用户去设置页「换播放器」不是产品行为 |
| IJK 零缓冲 | 弱网更容易花屏/卡顿；30 分钟场景应保留前向缓冲 |
| 弹幕无上限 + 每条动画控制器 | 长时直播内存与 UI 线程双涨 |
| 第三方明文签名服务 | 明文 HTTP、陌生服务器、单点故障 |

## 2. 参考实现 B：`chen-zeong/DTV`

### 2.1 它是什么（观测）

- **不是 Android TV 应用**：Tauri 2.7 + Rust + Next.js 16/React 19 的**桌面客户端**；播放是 WebView 里的 **xgplayer（HTML5 video + MSE）**，不是 ExoPlayer。
- commit `9cd1731`，v3.0.3；安卓版在另一个仓库 `chen-zeong/dtv_mobile`（未分析）。
- 四平台取流/签名/弹幕协议在 Rust 侧；前端负责播放器与弹幕层。

### 2.2 能抄 / 不能抄

| 能抄 | LiveHub 落地 |
| --- | --- |
| **斗鱼 300s 直链预取续流**：到期前 5s 预取，EOF 时接续 FLV tag，裁剪重复 GOP（`flv_relay.rs`） | 本工程没有本地 relay，改为 EOF/403/连续加载错误时**重新取地址**并回到同一条线；后续可做「预取 + 接续」消除空档 |
| 弹幕 WS 分级退避：普通断线 1s→30s；抖音 429/403 拉到 60–300s、504 10–120s、0–800ms 抖动；连上即重置 | 三家已有退避/看门狗；抖音弹幕 v1 不做 |
| 候选排序：虎牙 `tx→al→hs` 且优先 huya 域名；B 站 HLS 探测优先 `d1--cn`；斗鱼 scdn 靠后 | 本工程按 `sCdnType` 过滤 HS HLS、哔哩 HLS ts→fmp4→FLV 排序；探测会拖慢首帧，暂不做 |
| 瞬时网络错误只重试 1 次、180ms 间隔；HTTP/1.1 优先 | 本工程只对虎牙 profile 非 2xx 重试 1 次；其余交给线路切换 |

| 不能抄 | 原因 |
| --- | --- |
| 播放层零自动恢复 | 没有 error/stalled/ended 监听；断流只能手动刷新 |
| 所有取流失败一律「主播未开播」 | 网络错误/签名错误/房间不存在混成一个动作 |
| 只有斗鱼有续流 | 虎牙/B 站/抖音地址到期就停在最后一帧 |
| 无 telemetry、无长跑测试 | 出了问题无法复盘 |

## 3. 本工程的技术选型（结论 + 代价）

| 层 | 选型 | 为什么不选另一条 | 代价 |
| --- | --- | --- | --- |
| UI | Kotlin + Jetpack Compose for TV | 不用 Flutter：TV 遥控器焦点系统与硬解路径要原生；不用 WebView：10-foot UI + 焦点 + 硬解都不划算 | Compose for TV 下限 API 21；低端盒子动画要降级 |
| 播放 | Media3 1.4.1（ExoPlayer） | 不引 VLC/mpv/IJK：包体 + 生命周期 + 测试矩阵；Media3 覆盖 FLV/HLS/AVC/HEVC 硬解 | 极端 HEVC 10bit/HDR 可能解不了；错误会明说 |
| 网络 | OkHttp（唯一 HTTP 栈） | 不用 Dart/WebView 栈；OkHttp 自带 TLS，与 API 21 系统 TLS 解耦 | 无 |
| 取流 | 四家各自逆向接口 + 本地签名 | 不依赖第三方签名服务 | 平台改版要跟；抖音列表/搜索需 JS 签名，v1 不做 |
| 弹幕 | 四家 WSS 直连（哔哩 zlib、斗鱼 STT、虎牙 Tars） | 不引 protobuf/QuickJS 只为抖音 | 抖音无弹幕 |
| 持久化 | SharedPreferences + JSON | 不用 Room/DataStore：TV 盒子 IO 慢、内存小 | 无复杂查询 |
| 图片 | Coil 单例，无 crossfade，磁盘 64MB | 不用多套图片库 | 封面切换硬切（TV 上更快） |

## 4. 长时段稳定的七件事（本工程已实现）

| # | 能力 | 为什么必须有 | 实现锚点（搜符号） |
|---|---|---|---|
| 1 | **首帧判据** | `isPlaying` 不等于出画面；用 `playing` 做判据会让「有地址没画面」的线路被当成成功 | `LivePlayer` 的 `onRenderedFirstFrame` / `firstFrameRendered` |
| 2 | **停住看门狗** | 断流时常常没有 error；不检测就永远停在最后一帧 | `LivePlayer.startTicker` 的 `stalled`：每秒轮询 `videoDecoderCounters.renderedOutputBufferCount`；首帧后 8s 无新帧 / 重连后 12s 无首帧 |
| 3 | **EOF 处理** | 直播流被对端关闭时 ExoPlayer 认为「正常播完」 | `LivePlayer` 的 `STATE_ENDED` → `ended`；`PlayerScreen` 重连/换线/终态；虎牙先用同一 URL 快重连（首帧 ~150ms），再走新地址 |
| 4 | **重新取地址** | 地址会过期；同一个死 URL 反复 `prepare()` 会永远 buffering。同一次 `playUrls` 的所有线路共享 `expires`，所以多线路平台也不能靠换线绕过过期 | `PlayerScreen` 的 `reconnectReload` + `resumeLine` + `reloadTick++`；斗鱼走 `singleLineRetries`，哔哩多线路走 `expiryReloads`（错误含 CDN/过期时先重取 2 次再换线） |
| 5 | **加载错误升级** | 地址过期时 ExoPlayer 往往只报 `onLoadError`，不报 `onPlayerError` | `LivePlayer.onLoadError`：连续 2 次 403/404/410 且首帧后 2s 无新帧 → 置 error，触发重取 |
| 6 | **失败可见 + 可操作** | 「像崩溃」的体感来自「屏上什么都不说」 | `PlayerScreen` 的 `err` 门外原因条 + 失败态「重试」 |
| 7 | **遥测 + 追帧** | 没有真实分辨率/码率/丢帧/重缓冲，所有问题只能测到「黑屏」；直播落后窗口时换线是错的 | `LivePlayer` 的 `PlayerStats` + 每 30s `stats`；`ERROR_CODE_BEHIND_LIVE_WINDOW → seekToDefaultPosition()` |

补充与性能直接相关：
- **缓冲**：`DefaultLoadControl(5s/20s/1.5s/3s)`。5s 是最小维持，起播阈值是 1.5s。不照抄 IJK/mpv 的零缓冲。
- **解码方式**：设置里的自动/硬件/软件真的过滤 `MediaCodecInfo.softwareOnly`；过滤为空回落全部，不黑屏。
- **弹幕线程**：关闭时等 `onClosed` 1.5s，否则 `ws.cancel()`，避免 `loopReader` 挂到读超时。

### 4.1 研究复核后仍待处理的技术债

2026-10-30 的 Media3 复核确认了三处已修 + 三处待办：

**已修**
- `BEHIND_LIVE_WINDOW` 恢复补 `prepare()`：`onPlayerError` 后播放器在 `STATE_IDLE`，只 `seekToDefaultPosition()` 不会重新缓冲。
- 丢帧遥测口径：`onDroppedVideoFrames` 的 `droppedFrames` 是**增量**，不是累计；改为 ticker 读 `videoDecoderCounters.droppedBufferCount` 的累计值。
- LoadControl 文档语义：5s 是「最小维持」不是「起播」。

**待办（需要单独回归，不在本轮静默升级）**
- **Media3 1.4.1 偏旧**：1.8.0 修了「直播分片耗尽后 playlist 加载错误有时不上报」，1.11.1 修了 `HlsMediaChunk` 收到 `EOFException` 后的重试。升级到 ≥1.10 需要 compileSdk/AGP/Kotlin 联动（本机只装了 android-33/34），且必须重跑四平台 30 分钟浸泡。
- **HLS `EXT-X-ENDLIST` 与连接 EOF 未区分**：真下播的 manifest 有 ENDLIST，应直接进「主播已下播」终态；1.4.1 没有公开的 `currentManifest` getter，当前只能靠重取次数收敛。升级 Media3 后再接。
- **LoadErrorHandlingPolicy 未显式配置**：默认策略在弱网下可能过早判线路坏；可考虑 3 次指数退避后再换线，但要与「地址过期」的快速重取区分。

## 5. 四家接口的关键事实（代码与实测共用）

| 平台 | 事实 | 证据/后果 |
|---|---|---|
| 哔哩哔哩 | `getRoomPlayInfo` 的 `qn` 只是请求值，实际档位读 `codec[].current_qn`；不同房间可能固定签发某档 | 545068 请求 150/250/400/10000 都回 250（`accept_qn=[10000,400,250]`）；界面必须显示实际值 |
| 哔哩哔哩 | 匿名也能拿到原画的房间存在；未登录不是「一律压 250」 | 见 `android/docs/接口实测.md` §1.3.1 的逐房间表；不写比例 |
| 哔哩哔哩 | 房间不存在是 `code=60004`，不是 HTTP 404 | 必须映射 `ROOM_NOT_FOUND`，不能说「接口改版」 |
| 斗鱼 | `hlsH5Preview` 免签：`auth=md5(rid+秒级时间戳)`，`rid` 同时放 body 和请求头 | 只有一路「预览画质」；地址约 60s 后分片 403，必须重取 |
| 斗鱼 | 想要多档要回 `getH5Play` + 混淆 JS 签名 | 首版不做；不做第三方明文签名 |
| 虎牙 | anti-code 必须客户端重算：`wsSecret=md5(prefix_uid_streamName_seqid_wsTime)` | 接口给的 `wsSecret` 配自己的 seqid 会 403 |
| 虎牙 | `t` 必须取 antiCode 里的值（当前 102），不能写死 100 | 2026-10-30 对房间 660000/1995 的 antiCode 复现：t=100 → 403 text/html，t=102 → 200 video/x-flv；换房间/时间可能受 antiCode 生命周期影响，**结论是「取接口值」而不是「102 永远正确」** |
| 虎牙 | HS 的 HLS 只能走 HTTP | 同一串 antiCode：https 恒 403；http 实测 200/206 `application/x-mpegurl` |
| 虎牙 | FLV 每条连接只给约 1–2 MB 就被对端关闭（0.5–9s）；本环境实测给得最多的是 HS（≈2.2 MB）、AL（≈0.5 MB）、TX（≈0.14 MB） | 必须允许 EOF 重连；HLS 排前、FLV 按 HS→AL→TX 回落 |
| 抖音 | `reflow` 只认 19 位 `room_id`；`web_rid` 靠直播间页 `roomId`/`web_rid` 严格配对 | 配对失败宁可报错，不许猜 |
| 抖音 | 下播房间的 `stream_url` 仍给满 8 条，只是全死 | 在播判据只看 `room.status == 2`，不看地址是否存在 |
| 抖音 | 列表/分区/搜索/弹幕都要签名（`a_bogus` / `X-Bogus`） | v1 返回空列表 + 明说「本版不支持」，不伪造数据 |
| 抖音 | 在播 `web_rid` 可从**渲染后的** `live.douyin.com` 首页拿到（裸 HTML 没有列表）；`84873455143` → `7702431962371836710`，`status=2`，4 FLV + 4 HLS | 客户端 8 线 × 4 档实测出画面；抖音「本环境只有下播房」的判断已被推翻 |

## 6. 明确不做 / 以后再做

| 项 | 为什么现在不做 | 什么时候做 |
|---|---|---|
| 本地 FLV relay + tag 接续（DTV 的斗鱼方案） | 工程量大（自定义 DataSource/MediaSource），当前「重新取地址」已能让斗鱼续播 | 若测试显示斗鱼空档 >3s 且不可接受 |
| 多内核自动降级（Media3→软解→IJK/mpv） | 包体与测试矩阵；Media3 软解回退已开 | 有明确机型/编码不可播的现场证据 |
| ABR / 运行时降码率 | 四家直播接口不提供标准 ABR 清单；清晰度是重新取流 | v2 结合真实码率遥测 |
| 抖音签名（QuickJS/WebView） | 首版不引 JS 引擎；只影响推荐/搜索/弹幕 | v2 |
| 预连接/预取下一条线路 | 会增加首页/起播成本 | 有弱网首帧数据后 |
| 本地环形会话日志落盘 | 当前 logcat 统计够测试；落盘要设计导出与隐私 | v2 |

## 7. 证据与复现

- 参考 APK：REA（`identify_flutter_build` / `inspect_dart_aot` / `inspect_artifact`）+ 上游 `liuchuancong/pure_live` 1.7.4 源码对照（commit `355fb2f`）。`libapp.so` 只能做字符串/符号级观测，代码路径要么来自上游逐项对上，要么标为推断。
- DTV：`git clone --depth 1 https://github.com/chen-zeong/DTV`，commit `9cd17311fa32575fa68f7e79feafdb165c13edd3`；关键文件 `src-tauri/src/flv_relay.rs`、`src-tauri/src/platforms/*`、`web/src/components/player/MainPlayer.tsx`。
- 虎牙实测（2026-10-30）：对房间 660000/1995 的同一串 antiCode，`t=100` → 403 text/html，`t=102` → 200 video/x-flv；独立复核在不同房间/时间未能复现同一差分 ⇒ **实现必须取 antiCode 里的 `t`，不能把 102 写死**。HS HLS 的 `https` 恒 403、`http` 实测 200/206 `application/x-mpegurl`。**本机模拟器网络还会把 `hs.hls.huya.com` 的 HTTP 请求劫持到 `get360.rails.cn`**，表现为 manifest 解析失败；这是环境问题，应用应自动回落 FLV，不能据此判定 HLS 协议不可用。
- 斗鱼实测（2026-10-30）：预览地址约 60s 后 m3u8 403；应用需重取，不能只靠 `onPlayerError`。
- 哔哩实测（2026-10-30）：545068 四档请求都签发 250；线 1 HLS 分片 404 后应用自动换线。
- 本工程实测：`android/docs/接口实测.md`；稳定性测试：`android/docs/测试方案.md` 第 5 节；浸泡脚本 `android/tools/soak.py` + `android/tools/soak_summary.py`。

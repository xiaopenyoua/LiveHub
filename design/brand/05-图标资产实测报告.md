## 2. 数的来源：一套几何源，三处渲染

`design/.icon-geom.mjs` 是唯一几何源，`design/.icon-build.mjs` 从它生成全部产物。取整规则（02 §2）被写成代码，
并**反向断言它算出来的等于 02 表格写的**（`EXPECTED` 表逐项比对，不等就 throw）—— 五档全部通过：

```
档位  三角 w×h   底边x  顶点      徽章 w×h    徽章 x      缝     缝下限  闸门
48      25 ×  32    11     (36,24)     13 ×  6     23→36       3.10   2.56     未触发
72      37 ×  48    17     (54,36)     20 ×  9     34→54       4.22   3.84     未触发
96      49 ×  64    23     (72,48)     27 × 12     45→72       5.33   5.12     未触发
144     74 ×  96    34     (108,72)    40 × 18     68→108      8.44   7.68     未触发
192     99 × 128    45     (144,96)    53 × 24     91→144      11.54  10.24    未触发
```

**闸门（02 §2 第 4 条）五档一次都没触发**，不存在「徽章左缘左移 1px」的档。
坐标全部是 `k = P/72` 乘**绝对坐标**，没有一处比例连乘（连乘会掉到 2.19:1，见 §6 第 4 条）。

坐标系的铁律也写进了代码：`geom(P)` 走 72 视口（PNG / 512 母版），`L108` 走 108 图层（VectorDrawable）。
两者不互乘 1.5 —— 第一版脚本在这里踩过一次（把 `shapesAtExact(108)` 当成 108 图层，算出顶点 81），已修。

## 3. 五项硬自检（实测）

### 3.1 96px：徽章右缘与三角顶点**同一列**

```
徽章右缘最后一列 = 第 71 列（占 x∈[71,72)，该列红色覆盖率 91%）
三角顶点所在的最后一列 = 第 71 列
是否同一列：是，同一列 ✓
```

两条边都落在像素边界 `x = 72` 上（顶点 x = 72，徽章右缘 x = 72），因此在第 71 列收尾。

### 3.2 48px：缝里确实是纯黑，没有灰桥

逐列（徽章 x 23→35）数「徽章最低行」与「三角最高行」之间的像素：

```
列 x    徽章最低行   三角最高行   纯黑行数   缝内非纯黑像素
23       11        15        3        —
24       11        16        4        —
25       11        17        5        —
26       11        17        5        —
27       11        18        6        —
28       11        18        6        —
29       11        19        7        —
30       11        20        8        —
31       11        20        8        —
32       11        21        9        —
33       11        22        10       —
34       11        22        10       —
35       11        23        11       —
```

- 缝最窄一列 = **3 个完全不透明 `#000000`**（下限 3）→ 达标
- 缝内含纯黑像素的列数 = **13 / 13**
- 出现灰桥（缝内非纯黑像素）的列数 = **0**；缝内出现过的非纯黑值 = **空集**

灰桥是被**圆角本身**挡住的，不是靠运气：徽章左下角 `(23,12)` 是规格用来定义 3.10 的那个尖，全圆 r=3 把它整个切掉了
（左端圆弧的圆心在 (26,9)，最近点切在 (24.4,11.2) 附近），缝的最窄处因此从那个尖挪到了第 23 列
—— 那里是徽章左端极薄的尖端（该列红色覆盖率仅约 5%）与三角斜边之间的空隙，仍然是 3 个纯黑像素。

### 3.3 五档颜色集合：第四色 = 0 种

抗锯齿**没有关闭**。关掉会让 25° 斜边产生 1px 台阶，48 档会变成锯齿噪点 —— 而 02 §2 真正要防的是
「缝里两列半透明灰把两块连起来」，不是斜边本身。替代做法是**给每个非纯色像素一个合法定义**：

- 白与黑之间的 AA 只能是 `(t,t,t)`；
- 红与黑之间的 AA 只能是 `(t, t×69/255, t×58/255)`；
- 落不进这两类的，计「第四色」——真违规。

```
档    纯 #000000   #FFFFFF    #FF453A    边缘混合   占画布    第四色
48      1788       362        58         96      4.17%     0
72      4064       832        142       146      2.82%     0
96      7270      1494       268       184      2.00%     0
144    16400      3440       605       291      1.40%     0
192    29194      6186      1098       386      1.05%     0
```

**第四色合计 0 种**。边缘 AA 只在本色与 `#000000` 之间插值，没有引入任何新色相。边缘像素占比最高的一档是 48（4.17%），
随尺寸增大单调下降到 1.05% —— 这正好说明边缘量随周长走、墨量随面积走。

### 4.1 矢量回渲：把 XML 里的 pathData 原样拿去光栅化

`design/.icon-vectors.mjs` 从 `android-res` 的 XML 里**正则抽出 pathData 字符串**再喂给 Chrome，证明「写进 XML 的那串字母」真的画出规格里的形状；同时证明 SVG 文件与 XML 里的路径**逐字相同**。

```

                        monochrome tri ✓ 逐字相同 / pill ✓ 逐字相同

            右缘最后一列 71 / 顶点最后一列 71 → 同一列 ✓
            徽章高出三角顶 3 行（规格 0.06×48 = 3）
            缝内纯黑最窄处 5 像素，缝内非纯黑像素 0 个
```

## 5. 「规格与像素网格打架」的实情（五处，全部只影响怎么读，不影响图形）

1. **192 档宽高比写 2.21，实测 2.208。** `53 ÷ 24 = 2.2083`，02 §2 表里写 2.21 是取两位。两者是同一个数。
2. **48 档宽高比写 2.17，实测 2.1667。** `13 ÷ 6 = 2.1667`，规格 §3 表写「2.22→2.17」同样是取两位，
   但这一处方向是**往下**：如果有人拿 2.17 当硬下限做断言，48 档会以 0.15% 的误差踩在线上。
   结论不变（远大于裁决要求的 2:1），但校验脚本必须用「≥2.0 且落在 [2.16, 2.26]」这类区间，不能用 2.17 单点。
3. **96 档同一列要靠「任意覆盖」判色。** 顶点在 `x=72` 是像素边界，第 71 列只有 0.3 像素覆盖（像素值约 82/255）。
   用「白度 > 200」这种强阈值会把那个尖判没，得到「71 vs 70 差 1 列」的假失败。量的方法必须先定，再谈达标。
4. **「缝 4.22 单位」是名义值，量到的一定更宽。** 约束点是徽章**尖角** `(52,36)`，而徽章是全圆 r=4.5，
   这个角被圆弧切掉了 —— 实际最近点在左端圆弧的切点上。48 档实测两块实体（覆盖率≥50%）最短中心距
   **4.47px**（同一 48px 画布下名义值只有 3.10px）= 6.71 个 108 单位。方向是单向安全的（只会更宽），
   但 48 档「缝 3.1px」这句话在像素上对应的是**最窄列 3 个纯黑像素 / 最短中心距 4.47px**，
   验收时按 `≥3 纯黑且无灰桥` 判才对，按 `=3.1px` 判会要求把图改坏。
5. **红色墨量有两个分母。** 1.39% 是 108 图层画布，3.11% 是 72 视口画布（PNG 实际画布）。裁决 §3 自己就写了
   「1.39% 画布 / 3.1% 视口」，是同一块墨两个分母，不是两条互相打架的指标。

## 6. 复现

```bash
node design/.icon-build.mjs           # 几何断言 → 3 个 SVG → 五档 PNG → android-res 树
node design/.icon-preview-build.mjs   # 生成 design/brand/icon-preview.html
node design/.icon-shots.mjs           # 取证截图（含版面实测、字体实测、console 闸门）
node design/.icon-verify.mjs          # 位图五项自检（PNG 解码 + 逐像素分类）
node design/.icon-vectors.mjs         # 矢量回渲 + monochrome alpha 实测
```

依赖：node v22、`/Applications/Google Chrome.app` headless（无 npm 依赖，PNG 读写自带于 `design/.png.mjs`）。

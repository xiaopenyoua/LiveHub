## 0. 一句话结构

**深暖褐 16:9 圆角卡片 + 一枚双色字标（白 `Live` / 红 `Hub`）**，卡片浮在**更深一档**的暖褐底上，四周等比留白；横卡是主形态，方形是兜底；开屏就是把这枚卡放大到 1440×810，底与卡的差是 **ΔL\* 4.08**。
**关系与参考图一致（卡亮于底），只有绝对量级不同** —— 参考图是全亮（浅卡浮在暗底），v2 是全暗（`L\* 10.89` 的卡浮在 `L\* 6.81` 的底）。**形取自参考图，色取自用户指令，两者不冲突。**

**两个 L\* 是主理人算低了，四个操作性数字他全对。** 16.557 / 4.935 / 4.08 / 1.085 我复算与他逐位吻合，所以差的只是 L\* 换算本身，**不影响任何判定**。诊断线索：53.3 恰好是纯红 `#FF0000` 的 L\*（53.24），疑似按纯红算的；98.6 疑白点不同。**以本表为准。**

**「干净的暖」，不是「脏的褐」—— 这句话的物理内容是四个数：** 图标底 `#231C16` 的 **a\*=+2.21、b\*=+5.43、C\*=5.86**：暖在**黄红侧**（b\* 为正且大于 a\*），**彩度 5.86 低于 6** —— 彩度低到这一步，它读起来是「有一点温度的深色」，不是「褐色」。会变「脏」的褐是 b\* 高、C\* 高（比如 b\*≥12、C\*≥14 那种），这一步离得很远。

**用户说的「背景色稍稍有一点点变化」到底改了什么，可以精确到两个数：** 用户字标图 `ref-wordmark.png` 的底是 **`#121217`，b\* = −3.14**（中性的冷黑）；本方案图标底 **b\* = +5.43**。**b\* 从 −3.14 翻到 +5.43（+8.57），L\* 从 5.63 抬到 10.89（+5.26）—— 这就是「稍微改改背景色」的全部物理内容。** 不是换了一个色相，是把一支冷黑推到黄红侧一点点；a\* 只动了 +1.05。所以「稍微」这个词是有量化对应的，不是客气话。

**墨全部照用户原图，只有背景是设计的。** `Live` = `#FFFDFA`、`Hub` = `#FF453A` 都是 `ref-wordmark.png` 里逐像素量出来的原值（`Hub` 红墨众数 `#FF453A`，427 个像素；`Live` 最亮值 `#FFFDFA`），一个通道都没改。本方案在这张图上只做了两件事：**换底**（`#121217` → `#231C16`）和**排字**（§3 的光学尺寸与字距）。**底色是唯一被设计的东西**，字形、笔重、红白关系全部是用户的。

**红只有一支，且它就是参考图那一支。** 深底上 `#FF453A` 有 **4.935 : 1**，直接过 4.5，**没有任何需要补救的地方**；项目里不存在第二个红，也不需要第二个红。同理 `Live` 的 16.557 : 1 意味着白色不是勉强，是有 2.4 倍余量。

**四色封闭：出现第 5 个色值即违规** —— 任何灰、任何 alpha、任何「为了过渡好看」加的中间色都算第五色；唯一例外是抗锯齿在边界上**必然**产生的混合像素（那是渲染产物，不是色值）。与 08 §6 同一条。


## 2. 参考图实测：两处确认、一处推翻

**`ref-netflix-icon.png`（153×93，模糊源，按亮度 50% 阈值分割）**

| 项 | 主理人数 | 我实测 | 结论 |
| --- | --- | --- | --- |
| 底板 | 137×77 = 1.779 | 137×77，**1.7792** | ✓（16:9 是 1.7778，差 0.08%，属模糊） |
| **圆角 r / 板高** | **0.125** | **0.1558**（四角 11.6 / 11.7 / 11.9 / 12.8） | **推翻，见下** |
| 红字墨宽 / 板宽 | 0.745 | **0.766**（105 / 137） | 同一块墨的边缘归属差，用 0.766 |
| cap 高 / 板高 | 0.312 | 0.312–0.351（24–27px） | 取区间 |
| 上下留白 | 相等 | 24 / 26（差 2px = 2.6%H） | ✓ |

**圆角 0.125 是错的，正确值 0.155。** 主理人的对角探测法：沿 45° 找第一个亮像素得 d = 4px，按 `r = d ÷ 0.414` 反推 9.66。问题是 `0.414r` 在这个尺寸下只有 **4–5px**，±1px 的模糊就是 **±25%** 的 r —— 那不是测量，是猜。我换两种方法：

1. **四角边缘拟合**：逐行取亮区左/右端点，对 `inset(d) = r − √(2rd − d²)` 在 d = 2…10 上做最小二乘。四角各自 **11.6 / 11.7 / 11.9 / 12.8**，均值 **12.00** → r/H = **0.1558**，区间 **0.1506–0.1662**（左上角偏大是被板顶高光污染，取其余三角更可信：0.151–0.155）。
2. **退化检查**：若 r 真是 9.66，则 `inset(4)` 应为 2.1px、`inset(8)` 应为 0.3px；实测是 3 与 1，只有 r ≈ 12 对得上。

**取 r = 0.155H**（区间中偏保守）。三套画布的圆角全部由此重算，这是会**全线错**的那类数：`22.5 / 64 / 101.25` 全部作废，见 §4。**若原形是 iOS 式连续圆角（超椭圆），等价的圆半径还要再大 5–10%，所以 0.155 是下限，不许再往下调。**

**`ref-wordmark.png`（144×59）**：墨迹 **112×24**（cap 23–24）→ 宽高比 **4.67–4.87**；`Live` 墨 x 19–74、`Hub` 墨 x 75–129；**分界 = (75 − 19) ÷ 112 = 50.00%** ✓；`Hub` = `#FF453A`。

### 2.1 两张参考图的颜色：它们的「底」不是同一个东西（v1.1 新增）

这一节只干一件事：**证明「形取自参考图、色取自用户指令」不是一句遁词。**

| 参考图 | 取色（逐像素） | L\* | 它是什么 |
| --- | --- | --- | --- |
| `ref-netflix-icon.png` | 板 `#CFF0FF` | **92.93** | **浅色板**，浮在模糊暗景上（暗景 `#402F34` / `#804E48`） |
| `ref-wordmark.png` | 底 `#121217`；`Live` 最亮 `#FFFDFA`；`Hub` 众数 `#FF453A`（427 px） | 底 **5.63** | **深底**，白字红字压在上面 |

**两张图的「底」根本不是同一个东西：图标参考是「浅板浮在暗景上」，字标参考是「白+红压在暗底上」。** 所以谁要是把字标那张图的**展示背景**（`#121217`）当成图标底、又把字标自身的白直接抄进图标，就会得到一份「深底 + 白板」的错版 —— 那不是我做的方案，也不是用户要的方案。

本方案的读法只有一句：**板要亮于底（这条取自图标参考图的关系），但板要暗（这条取自用户「干净暖色系」的指令）。两者不冲突，因为一条管关系、一条管量级。** v1.1 的板 `#231C16`（L\* 10.89）比底 `#1A140F`（6.81）亮 4.08 —— **关系的符号与参考图一致（板亮于底），绝对值从 +90 缩到 +4.08。** 参考图是全亮，本方案是全暗。

> 取数方法：这张表由 `testing-evidence-collector` 用 `design/.ev-v2-ref.mjs` 逐像素统计得出（众数 + 最亮值），我复核了 `#FF453A` 与 `#FFFDFA` 两个值落在众数/极值上，与 §1 完全吻合。


## 3. 字标排版参数：本节是全篇最大的一处修正

| 参数 | 值 | 出处 / 为什么 |
| --- | --- | --- |
| 字族 / 字重 | Inter **600** | `assets/fonts/InterVariable.woff2`（可变字体，轴 opsz 14–32、wght 100–900） |
| cap 高 | **0.72754 em** | `OS/2.sCapHeight = 1490 / 2048`，两个 opsz 实例完全相同 |
| 字距 | **−0.02em** | 上一版沿用；深底大字号同样成立（字距与底色无关） |
| 排版（advance）宽 | **3.6300 em** | `Live` 1.8755 + `Hub` 1.8745 ＋ 6 × (−0.02)，**@ opsz 32** |
| 墨迹宽 | **3.53906 em** | 同上实例的 ink bbox（左副距 0.0603、右副距 0.0306） |
| **墨宽 ÷ cap** | **4.864** | 3.53906 ÷ 0.72754。后面 §4 的闭式规则靠这个常数 |

**3.847em 不成立，正确值是 3.6300em。** 3.847em 是 `opsz = 14`（正文光学尺寸）下的宽：raw 3.9873 − 7 × 0.02 = **3.8473**。而本方案的字号是 69 / 111 / 312px，**浏览器会把可变字体的 `opsz` 自动切到 32**（CSS `font-optical-sizing: auto` 是初值），那时宽只有 **3.6300em**，比 3.847 窄 **6.1%**。三条证据：

1. **对参考图**：参考字标的墨宽/cap = **4.67–4.87**；Inter 600 @opsz 32 = **4.864**（差 ≤ 0.1%），@opsz 14 = **5.156**（差 5.9%）。参考图的字是 display 光学尺寸画的，只有 32 对得上。
2. **对实现**：不显式关掉，得到的必然是 opsz 32 —— 写 3.847 就是写了一个浏览器不会给你的数。
3. **对内部一致性**：48 方形字号只有 10.4px，浏览器给 opsz 14；开屏 311.8px 给 opsz 32。**同一个 logo 在 48px 和 1440px 上比例不同** —— 这与 02 §0「两套坐标系混用」是同一类错，只是这次错的轴是光学尺寸。

**结论（写进实现纪律）：`font-optical-sizing: none` + `font-variation-settings: 'opsz' 32`，全尺寸锁死。** 锁死之后才有唯一的宽高关系，§4 的表才有意义。

**一条闭式规则生成三套画布（不用手推）：**

> **cap / H = 0.7663 × (W / H) ÷ 4.864 ≈ 0.1575 × (W / H)**
> 即 **字号 = 0.786 × W ÷ 3.6300**、**advance 宽 = 0.786 W**、**墨宽 = 0.7663 W**、**cap = 0.72754 × 字号**、**cap 顶 = (H − cap) ÷ 2**、**r = 0.155 H**。

这条式子顺手解释了主理人对 B 的那段手推：**「方形不能照抄 0.28H，cap 必然变矮」是对的，但它不是特例 —— 只要 W/H = 1，同一式子就给 0.1575，因为 cap 受宽度约束、宽度受板宽约束。** 三条画布只有 W/H 一个变量。

- **C 的卡在屏上**：1440×810 居中 → x **240–1680**、y **135–945**（左右各 240 = 12.5%，上下各 135 = 12.5%，四边等比 ✓）；卡内 cap 顶 / baseline 换到屏坐标是 **426.58 / 653.42**，cap 中心 = **540 = 屏心** ✓。
- **上下留白 = (H − cap) ÷ 2**，三套一律「cap 上下等距」。参考图 24 / 26 就是这条（差 2px 是模糊，不是设计）。
- **墨留白 11.68%W 与参考图 10.95% / 12.41%（左/右）的均值逐位相同**，这是 §3 那条规则没算错的旁证：换对 opsz 之后，宽度和留白同时对上参考，一处都没调。**但要看清楚这个 11.68% 是哪把尺的量法** —— 它等于「墨迹框居中」，即 (W − 0.7663W) ÷ 2；表里这一列就是按这个口径给的。**CSS 实际给的是 advance 框居中，见 §6.1，两者差 4.65px（1440 档）。**
- **A 与 C 严格是 4.5 倍关系**（1440 ÷ 320），不是「差不多」：`69.29×4.5 = 311.81`、`50.41×4.5 = 226.85`、`251.52×4.5 = 1131.84`、`27.90×4.5 = 125.55`。所以开屏可以按 A 放大实现，误差 0。
- **48 那一行是「方形兜底」缩到 48，不是横卡缩到 48**（v1.1 明确，堵一处会画错一个版本的歧义）：画布 **H = W = 48**，故 r = 0.155 × 48 = 7.44、cap 顶 = (48 − 7.56) ÷ 2 = 20.22。若真按 16:9 把板高压到 27.11，r 会变 **4.19**、cap 顶变 **9.72** —— 差一倍。**48 档按本表（方形）。**
- **48 档没有「底」，板就是画布**：A / B / 48 三套的板都占满画布，只有 C（开屏卡 1440×810 放在 1920×1080 里）才有 §7 那条卡片边界。所以 §7 的 ΔL\* 4.08 **只在开屏出现**，不要往图标资产里加「底」。

`L` 干 **0.1234em**（比 `H` 的 0.1304em 更细，所以由 `L` 定门槛）→ em ≥ **16.21px** → 字宽 ≥ **20.17px（48 档的 42.0%W）**。0.62W 给 29.76px = **1.48 倍余量**，四项（字宽 / em / 干 / cap）同比例通过，**可以直接用，不需要调**。

> **两个流传的错数要在这里掐掉**：① 08 §7 正文里还留着旧门槛「≥19.5px（41%）」，那是没乘 advance 比的中间值，正确门槛是 **20.17px**（em 16.21 × 1.2446）；② 「字宽 ≥20.9px（43.5%）」这个修正数是按 `LH` advance = 1.2886em 推的 —— 1.2886 是我上一版把 `L`/`H` 的 advance 记错了（见 §6 末的订正），**真值是 1.2446，所以 20.17 对、20.9 错**。

**分界不沿用 50.7%：`LH` 是 47.14%。** 两个字母时，`H` 的左副距占墨宽的比例从 1.71% 涨到 5.37%，所以同尺（红墨左缘 ÷ 墨宽）下期望值是 **47.14%**，容差同样 ±1.0pp。**拿完整字标的 50.7% 去验收 `LH` 会得到一次 100% 的假失败。**

**横卡与方形不是缩放关系，是两种构成：** 完整字标在 48 档 cap 只有 7.56、竖干 1.28；`LH` 在 48 档 cap 17.40、竖干 2.95。**同一个画布上 cap 差 2.3 倍、干宽差 2.3 倍** —— 这不是「大一点」，是换了一套构成。所以「方形档用 `LH`」这句话真正的意思是：**字标宽度比从 0.786 改成 0.62 只是表面，真正的变量是字号 —— 从 `0.2165W`（10.39 @48）变成 `0.4982W`（23.91 @48），涨 2.30 倍。** 难读的不是「字标太宽」，是「七个字母把字号压到了 0.2165W」。

## 5. 48px 可读性：救不了，写清代价

**数：** 字号 **10.39**、cap **7.56**、x 高 **5.67**、每字 advance **5.39**、竖干（`l` 的干宽 0.1234em）**1.28px**。3 米处按 0.635mm/px：cap **5.50 弧分**、每字 **3.92 弧分**、x 高 **4.13 弧分**、竖干 **0.93 弧分**。

**为什么这是必然失败而不是「小一点」：** 20/20 的定义是 **Snellen 字母总高 5 弧分、笔画 1 弧分**。我们的 x 高 **4.13 < 5**、笔画 **0.93 ≈ 1 弧分极限** —— 48px 恰好压在视力极限上，不是「勉强可读」，是「读不读得出来取决于当天视力」。且竖干 1.28px 在光栅上只能渲染成 **1 个实心像素 + 两条约 60% 的灰边**；现在底是深暖褐 `#231C16`，这两条灰边**比红更接近底色**，于是字先糊成「一条红」，再糊成「一条暗红」。**深底比浅底更糟**：浅底上灰边是「字变淡」，深底上灰边是「字变细」，而细到 1px 就是消失。

**不救，也不许救。** 能救的两条路都违背方案：加粗到 800 会改掉用户给的字形；拆成两行会破坏 §6 的双色分界。**这是方案的固有代价** —— 参考对象靠全球品牌记忆兜底，LiveHub 没有这个兜底，只能靠形状。

**把影响面收窄（这段是给验收用的）：** 用户在 TV 桌面实际看到的是 **320×180 的 banner（§4 A，cap 50.4px，每字 26.1 弧分，可读）**；48 平方只出现在 Android 自适应图标与商店缩略图，那两处的任务是**形状记忆**不是读取。48px 下能保住的只有两件事：**一块深暖褐的 1:1 圆角板**与**一条红**。

**所以 48 方的验收判据只能写：「卡形（1:1 方形板 + r 0.155H = 7.44）与红条位置正确」。不得写「字可读」—— 写可读就是写了一条必然失败的判据。**

> 这里 v1.0 写的是「16:9 圆角卡」，**是错的，v1.1 改正**：48 档是**方形兜底**（§4 那一行只有 H = 48 才给得出 r 7.44 / cap 顶 20.22）。若真按 16:9 缩进 48 宽，板高只有 27.11、r 4.19、cap 顶 9.72 —— **差一倍，整行数都要换**。这一句如果留着，前端会画错一版。

**参考值 50.00% 成立，但它是一把特定的尺量的：`红墨左缘 ÷ 墨迹总宽`。** 同一个字标在五把尺下有五个数（全部由 fontTools 在 Inter 600 @opsz 32 上直接量，不是推算）：

**容差（写死，下面两把尺二选一，不许混用）：**

- **用与参考同尺（推荐给取证）**：红墨左缘 ÷ 墨迹总宽，期望 **50.73%**，容差 **±1.0pp**，即 **49.73–51.73%**。为什么不是 50.0：参考图的 `H` 与 `e` 是另一套字体，各自的侧副距不同；`e` 的右副距 **0.0288em**、`H` 的左副距 **0.0603em**（2.1 倍），加一个 **−0.02em** 的字距构成 **0.0691em** 的黑缝，且缝整体偏 `Hub` 侧 —— **这 0.73pp 是字体决定的，不是渲染误差**。
- **用 advance 边界（推荐给前端）**：÷ advance 总宽，期望 **50.01%**（≈ 恒为 50%，因为居中就是按 advance 框做的），容差 **±0.2pp**；这条不用数像素、可以纯计算，**等价于验收「居中没被手调过」**。
- **五把尺最大差 1.70pp，混用必出假失败** —— 这是 03 §11 那类「把对的图判死」的同一个坑。**同一份报告里出现两种尺的百分比，报告作废。**

**「落在 50% 是巧合还是必然」：必然，且精确到 0.05%。** Inter 600 @opsz 32 下，`Live`（4 字符）advance **1.8754em**、`Hub`（3 字符）**1.8745em**，差 **0.0009em = 0.05%**。原因是窄字与宽字恰好抵平：`i` **0.2324** + `L` **0.5498** = 0.7822 是窄的，`H` **0.7148** + `b` **0.5869** = 1.3017 是宽的，4 对 3 正好扯平。**反向佐证**：在 opsz 14 下两者差 **1.19%**（2.0054 / 1.9819），50% 反而不成立 —— **这是 §3 该锁 opsz 32 的第四条证据。**

> **v1.1 订正**：v1.0 这一段的单字 advance 写的是 `i` 0.2422 / `L` 0.5654 / `H` 0.7432 / `b` 0.6123 —— **四个数都大了 2–4%**（那是另一份表里的值，我没回查就抄进来了）。四个数的**和**（1.8755 / 1.8745）没错，所以 §3 的 3.6300em 与 §4 的三套几何**一个数都不用改**；错只错在单字分解，以及由它推出来的「`LH` 门槛 20.9px」（见 §4.5）。**这就是为什么规格里的每个派生数都要能从原始表倒推回去。**

**但墨量仍不对称：** `Live` 墨宽 1.7263em / `Hub` 1.7436em（差 **1.0%**），与已作废的老字标 `Live` 8207 : `Hub` 8721 同类。**所以不要用墨量判分界**，用宽度判。

### 6.1 居中按哪把尺：advance 框，不是墨迹框（v1.1 新增，差 4.65px）

1440 档（字号 311.80）：

| 居中方式 | origin x | advance 边界 | 红墨左缘 | 墨迹中心 | 左留白 / 右留白 |
| --- | --- | --- | --- | --- | --- |
| **按 advance 框（CSS 默认）** | 394.10 | **960.14** | 972.74 | **964.65** | 172.90 / 163.61 |
| 按墨迹框（有些设计工具） | 389.45 | 955.49 | 968.10 | 960.00 | 168.26 / 168.26 |

**两种居中差 4.65px（0.32%W；55″ 3 米处 3.39 弧分）。** 这不是小事：`08 §6` 的验收判据写的是「分界线落在 **960 ± 1**」，——**按 advance 居中它落在 960.14（通过），按墨迹居中它落在 955.49（判死）**。同一个正确的实现，只因为居中方式不同就被判违规，是典型的假失败。

**所以写死：按 advance 框居中（也就是 CSS `text-align: center` / flex 居中的天然结果，零额外工作），验收对 960 ± 1。不要为了「看起来更居中」手动左移 4.65px** —— 那会把 `08 §6` 的判据打掉，而且在 55″ 上这 4.65px 根本看不出来（3.39 弧分，低于 §11 那套 40″–72″ 的检测阈）。

**参考图不能裁决这件事**：图标参考图文字左右留白是 15 / 17（左小 2px），方向与 advance 居中的 172.90 / 163.61（左大）**相反**；但 2px 在 137px 的模糊源里就是噪声量级，不足以下判断。**这条只能靠实现侧定，不能靠参考图推。**


## 7. 卡片边界 1.085:1：正当性 + 色带判定条件

**数：** ΔL\* **4.08**、亮度比 **1.085 : 1**、绝对亮度差 **ΔY 0.00491**、Weber 相对差 **39.4%**（Michelson 24.6%）。

### 7.1 为什么「看得见」和「不违规」可以同时成立 —— 它们是两个问题

- **看得见**：用户看到的是**一块面**（1440×810 对 1920×1080），这正是用户要的「稍稍有一点点变化」。人眼对**相对**亮度差敏感，39.4% 是大色块辨别阈（约 1%）的 **39 倍**。
- **不违规**：WCAG 1.4.11 管的是「**识别控件与状态所必需的**视觉信息」≥ 3:1。卡片边界不承载任何状态、不参与任何操作、删掉它不影响任何判断 —— **它不是「所必需的视觉信息」**，所以 3:1 不适用。**它是材质层次，不是信息层级。**
- **它承载的只有一条语义**：「这张卡是图标的放大版」。这条语义由**底与卡同时出现**表达，不由边界线表达。

**否决句（原样进 review 清单，不加「建议」「宜」）：**

> **一旦给卡片加描边、投影或外发光，这条 1.085:1 的边界就从「面」变成「线」。线是图形构件，按 1.4.11 必须 ≥3:1，而 1.085 不达标 —— 立刻违规。加边框的代价不是变丑，是把一处合法的材质改成一枚违规的构件。**

还有一条比合规更硬的：**卡是「图标的放大版」，给卡加描边就等于宣布图标也有描边，而图标没有。** 两处一旦不一致，「放大版」这句话就不成立了。

### 7.2 深底把这件事的性质改了：从「合不合规」变成「画不画得出来」

这是 v1.1 唯一一处**论证需要变强**的地方，因为换底之后两个量朝相反方向走了：

| 量 | 浅底版（作废） | 深底版 | 变化 |
| --- | --- | --- | --- |
| 绝对亮度差 ΔY | 0.0796 | **0.00491** | **÷16** |
| Weber 相对差 | 8.8% | **39.4%** | **×4.5** |
| ΔL\* | 3.39 | **4.08** | +0.69 |
| 8bit 码值跨距 | R 8 / G 10 / B 12 | **R 9 / G 8 / B 7** | **几乎没变** |
| 单码值台阶带走的相对亮度（G 通道） | **0.67%** | **3.87%（卡）/ 4.77%（底）** | **×5.8** |

**最后一行是这件事的全部要害：码值跨距没变（还是 8–12 级），但同样一个码值在暗场带走 5.8 倍的相对亮度。** 这是 sRGB 的 gamma，不是谁的错 —— 但它意味着**「浅底上够用的 8bit 余量」在深底上不能照抄**。

**「看得见」这一半更强了（相对差 39.4%），「能画出来」这一半变脆了（绝对差只剩 0.0049）。** 所以浅底版只需写正当性，深底版必须加判定条件 —— 不是谨慎，是这一段确实多了一个失效面。

**先排除量化（这是好消息）：** 8bit 下两色码值是 `(35,28,22)` 与 `(26,20,15)`，**逐通道差 (9,8,7)**；单个码值台阶的 ΔL\* 只有 **R 0.13 / G 0.34 / B 0.03**，而 4.08 的落差要跨 **12（按 G）/ 32（按 R）** 个台阶。**所以「4.08 在 8bit 上画不出来」是错的，8bit 绰绰有余，两个纯色面本身没有风险。**

**真正的失效面是「过渡」不是「台阶」：** 两块**纯色**面直接相邻时，中间不存在任何码值，风险为零；但只要中间出现**任何过渡**（渐变、插值、压缩重建），过渡区就变成一串台阶，而每一级在暗场带走 **3.9–4.8%** 的相对亮度。一条 1–2px 的插值过渡，在 55″ 3 米处宽 **0.73–1.46 弧分** —— 在暗场这就是一条**看得清的边**，不是色带就是描边。


### 7.3 判定条件：四种情况会出色带，以及怎么验

**会在这些情况下显色带（前三条是实现选择，第四条是硬件）：**

1. **用视频 / 动图承载开屏**（HEVC / WebM / AVIF / 帧序列）：DCT 在近黑区把 4.08 抹平，重建出的边界带振铃。**开屏这一段必须是纯色 `drawable` + 静态图，不得用视频或动图。**
2. **任何柔化**：模糊、阴影、外发光、径向渐变、毛玻璃 —— 它们把「面」变成「数得清的台阶」。
3. **非整数倍位图缩放**：双线性插值在边界造出中间码值，视觉结果不叫色带，叫**一条 1–2px 的亮边**（等价于描边，直接撞 §7.1 否决句）。**开屏卡必须按目标分辨率出图或用矢量，不许把 1440 宽的图拉到 1920。**
4. **OLED near-black 伽马 crushed**：部分面板把码值 0–16 压成 0。我们的底在 15–26、卡在 22–35，**恰好压在危险区边缘**。这是唯一「实现完全正确也会出事」的一条，所以必须有下面第 2 步。

**怎么验（三步，缺一不可）：**

| # | 动作 | 判据 | 不合格说明 |
| --- | --- | --- | --- |
| 1 | 截图上在卡心、底上各取 3 点 | 必须**严格**等于 `#231C16` / `#1A140F`；出现任何中间值 | 有渐变 / 压缩 / 缩放，回查管线 |
| 2 | 目标机实测（**OLED 与 LCD 各一台**） | ΔL\* 必须落在 **2–8** | <2：面板 black crush 吃掉了落差，换底或抬卡；>8：有人抬了 L\*，回到 `#231C16` |
| 3 | 8bit / 10bit 对照 | **10bit 下色带消失 → 是量化，可接受**；**10bit 下还在 → 不是量化，是渐变/压缩/缩放** | 后者必须修资产，不许用「面板问题」结案 |

**第 3 步是这一节的核心**，因为它把「看起来有色带」这个主观投诉变成了一个二值诊断：10bit 是 8bit 的 4 倍精度（4.08 跨 **128** 级），量化造成的色带在 10bit 上必消失；**只要 10bit 上还在，就一定是有人往中间加了东西**。

**圆角抗锯齿是唯一合法的过渡，但它正好压在下限：** 圆角边缘的中间像素各拿一半，ΔL\* ≈ **2.04** —— 落在第 2 步判据的**下界**。所以：**圆角可以有 1px 的软边（那不是「线」，是过渡），但圆角半径不许「为了更圆」再加抗锯齿羽化**，那会把软边从 1px 扩到 2–3px，扩出来的就是一条可见的边。

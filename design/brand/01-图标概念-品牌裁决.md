## 0. 结论先行

**母题：在播键（The Live Key）**，即第四方向。一块白色右向三角，加一枚压在它右上肩的红色圆角条。

一句话讲清它凭什么赢：**三个候选里只有它能在 3 米外被认出来，而「红色」在这个图形里回到它本该在的位置。**

四条裁决，不留余地：

1. **A 换台隐喻：否决。** 不是概念错，是它在图标尺度上必然退化成噪点。现有 banner 那组频道条是 8 列 × 6 段 = 48 个可辨特征，而 48px 图标的特征预算是 16 个。承接一个在目标尺度上不存在的形状，不是连续性，是假连续性。
2. **B 聚合隐喻：否决。** 聚合是入场券，换台才是差异点；把入场券画在门牌上，等于告诉用户「我和别人一样」。且 4 条汇入线在 48px 下每条只剩 4px 宽，低于 3 米可分辨阈值。
3. **C 播放 + 在播（现状）：否决其红色，保留其骨架。** 现状真正的错不是「通用」，是它把 `.livedot`（Ø12px 正圆红点）这个**状态符号**拿来当品牌装饰。全站只有一条纪律是硬的：红色等于正在直播。现状图标正在亲手稀释它。
4. **红色：保留，但换形状。** 圆点归状态，徽章归图标。图标里的红不是指示灯，是复刻应用里 `.card__live` 那枚压在封面右上角的红徽章。

**对 UI Designer 最重要的一条约束：图标里禁止出现正圆红点。** 红色构件必须是宽高比 ≥ 2:1 的圆角条，且与白色三角之间留 ≥0.08 倍三角高的黑缝。

## 2. 三案对比（另附第四方向）

评分 1–5，5 最好。「被抄风险」列 5 = 最难被抄。

| 维度 | A 换台隐喻（频道条 / 拨盘 / 递进条块） | B 聚合隐喻（四源汇一口） | C 播放 + 在播（现状） | **D 在播键（裁决）** |
| --- | --- | --- | --- | --- |
| 3 米辨识度 | **1** 需 48 个特征，超预算 3 倍 | **2** 每条线 4px≈1.6 弧分，低于阈值 | **5** 2 个块 + 1 缝 | **5** 2 个块 + 1 缝 |
| 与产品概念相关性 | **5** 直击第一根柱子 | **3** 聚合是入场券不是差异点 | **3** 说了「视频」，没说 LiveHub | **4** 说了「在播」，并复用卡片解剖 |
| 与现有资产连续性 | **2** 只在 banner 尺度成立，图标尺度断裂 | **1** 字标里没有「源」 | **3** 红点守住了红，但借了状态符号 | **5** 与字标、与卡片各对上一条硬规则 |
| 被抄风险（5=最难抄） | **5** 品类内无人用 | **2** 每个聚合器都画源→汇 | **1** 品类默认句式 | **3** 骨架通用，但「顶点对齐 + 徽章非圆」可主张 |
| **合计** | **13** | **8** | **12** | **17** |

**A 为何死**：概念本身是全案最好的，所以必须说清它死在哪。简化到 3 列之后，它变成「三根递进的竖条」，也就是信号强度格 / 均衡器 / 加载动画的通用图形，被抄风险从 5 掉到 1，而 3 米辨识度仍然只有 3，A 的两端都是墙。另有一处内伤：现有频道条**全部等高**，等高即零信息，它无法表达「换」这个动作，只能表达「有一排东西」。一个不能表达动作的换台隐喻，不该当母题。

**B 为何死**：除分辨率之外还有两条。其一，4 源汇 1 口在去掉分子图修辞后，剩下的唯一可辨形态就是「四条线 + 一个点」，恰好还是任务明令禁止的分子图。其二，四个平台不该被画成四条线，因为规范明令**不使用四家平台品牌色**，四条同色线等于宣称四家没有区别，跟产品的真实主张（房间号原样显示、平台名照实标）是反的。

**C 为何死**：C 的骨架（单一大块 + 右上小红）是对的，而且它一直是几何上唯一可行的构图（见第 3 节安全圆推导）。它错在红：`.livedot` 是全站的定义性符号，Ø12px 正圆，出现在卡片 LIVE 标、播放页状态、在播列表。把同一个正圆红点缩小塞进图标，等于把「红色 = 正在直播」这条纪律降级成装饰。品牌最贵的资产就是这条纪律，不能自己先花掉。

**D 凭什么比三者好**：D 不是 C 的妥协版，它换掉了 C 的语义主体，C 的红是**状态指示灯**，D 的红是**场景条上的徽章**，同一个颜色、两种物件、两套语法。四条同时成立且互不折扣：① 单一大块，48px 下 3 个特征，辨识度与 C 同级；② 红从「状态符号」改为「品牌构件」，纪律不破；③ 与字标同构（白色主体 + 右端红色构件）、与卡片同构（画面块 + 右上红徽章），连续性满分；④ 有一处可主张的独家规则（徽章右缘严格对齐三角顶点 x），使它不是「随手拼的播放键」。

## 3. 最终母题的形状（照着画）

**坐标系**：108 × 108，画布中心 (54, 54)，Android 自适应图标前景层标准尺寸。安全圆 Ø66（半径 33，同心）；视口 72 × 72（四边各留 18）。所有数字同一单位。

| 项 | 白色三角 | 红色徽章 |
| --- | --- | --- |
| 形状 | 右向等腰三角，**尖角，不圆角** | 圆角条，四角半径 = 高度一半（r = 4.5，全圆，对应 `--r-pill`） |
| 尺寸 | 37 × 48 | 20 × 9（宽高比 **2.22 : 1**） |
| 位置 | 底边竖线 x = 35，y 30 → 78；顶点 (72, 54) | x 52 → 72，y 27 → 36 |
| 关键约束 | 高宽比 **1.30**（不是等边的 1.16，不是方的 1.00）；几何中心 y = 54 与画布中心重合 | **右缘 x = 72，与三角顶点 x 严格相等**（本标记的独家规则）；顶边 y = 27，比三角顶边（30）高 3，即骑在三角肩上，不陷在三角体内 |
| 与对方的关系 | — | 与斜边的**名义**最小黑缝 4.2 = **0.088 × 三角高**，量到徽章 bbox 左下角 (52, 36) —— 这是**虚点**，全圆 r = 4.5 已把该角整个切掉（角点落在圆弧外 1.864）。**实体间距 = 5.94 = 0.124H = 1.41 × 名义值**，最近点在圆弧上 (54.05, 35.27)。两个数都要知道：前者是绘制控制量，后者是渲染后量到的值。见 §7.4 |
| 相对 72 视口 | 宽 51%，高 **67%** | 宽 28%，高 12.5% |
| 安全圆 | 底角半径 30.6，留边 2.4 | 右上角半径 32.4，留边 0.6（这是全图最紧的一处） |
| 48px 实际 | 24.7 × 32.0 px | 13.3 × 6.0 px |

**换任何画布尺寸都照下面这十条缩放，不要重算坐标**
```
三角高 : 三角宽        = 1.30 : 1        徽章宽 : 三角宽   = 0.54 : 1
三角高 : 视口高        = 0.67 : 1        徽章右缘 x        = 三角顶点 x（严格相等）
徽章高 : 三角高        = 0.19 : 1        徽章顶边高出三角顶边 = 0.06 × 三角高
徽章宽 : 徽章高        = 2.22 : 1        与斜边最小黑缝    ≥ 0.08 × 三角高（名义值，实体 ×1.37–1.43）
白色墨量 : 红色墨量    ≈ 5.5 : 1         红色墨量          = 1.39% 画布 / 3.1% 视口
```

**光学校正**：包围盒 x 35→72、y 27→78，中心 (53.5, 52.5)，相对画布中心左偏 0.5、上偏 1.5。这是刻意的：右向三角的质量在左侧，严格几何居中会显得整体右飘；且徽章补在右上、视觉重心上移。允许 ±1.5 单位内微调，不再另行居中。

**待裁项（立档，不在本裁决内）**〔v1.3〕：开屏 lockup 里图标按**包围盒**居中于 x = 960，但按墨量算的质心在 **947.8**，比轴心偏左 **12.2px**，3 米处折 **8.9 弧分**（12.2 × 0.635mm/px = 7.76mm）。作为参照：只算白三角时质心偏轴 18.5px，右上徽章已把它拉回 6.3px，也就是说徽章在**改善**平衡而不是制造失衡。
判据：**质心 ≠ 视觉平衡。** 观者判断的是轮廓与墨量的分布，不是物理质心；拿质心去挪一枚有方向感的标记，很容易挪成"歪掉的播放键"。故本项**不据质心裁决**，而由 team-lead 用 `design/splash.html` 1920 定稿帧按 3 米张角实测后决定。若动，只动开屏这一处并给出具体偏移量，**不动图标本体**。（质心 947.8 是对先前口头报的 947.6 的 0.2px 精算修正。）

**〔v1.3.1 补注〕两条口径，防止这个数被算成另一个数、或被「修好」得更坏：**

- **口径：等权面积矩，不是亮度加权。** 亮度加权（`#FF453A` 相对亮度 ≈0.25，徽章 1255 折成 ≈309）得质心 **943.3 / 偏 16.7px**，与等权差 **4.5px ≈ 现值的 37%**。两种口径都不算错，但判据只能用一种 —— 本裁决取**等权面积矩**（与本节墨量表同源）。覆盖率 / α 加权在硬边矢量上与面积矩恒同值，不构成第三种分岔。另：6852（三角）＋ 1255（体育场徽章）＝ **8107**，与 03 §3 逐像素实测的「图标墨 8107」撞在同一个数上 —— 形状公式与像素计数两条独立路径互验通过。
- **可测量：被感知的居中量是墨迹包围盒中心，不是质心。** 包围盒中心 958.61 → 偏 **1.39px ＝ 1.0 弧分**（0.635mm/px、3m），落在常见对称判别阈与两线分离阈之间（约 0.67–1.2 弧分），即**刚到阈值、不构成可辨缺陷**。反过来算：若真按质心把图标右移 12.2px 去「居中」，包围盒中心会变成偏 **＋10.8px ＝ 7.9 弧分**，比现在坏 **7.8 倍**。**「按质心居中」这个动作本身会让唯一可测量的居中量恶化近 8 倍** —— 本项不据质心挪图，自此不只是品味，有同尺自比的实测依据。（弧分阈值为外部文献量级，仅作参照带、不作本裁决的推导依据；本项只依赖那组 7.8 倍的自比。）

## 4. 必须避免（画错一条就不是 LiveHub 了）

1. **单一实心播放三角，无徽章。** 品类默认句式，等于没做。
2. **播放三角装进圆角矩形 / 圆形底板。** 最容易被误认为别家 App 的句式。本图标**不设容器**，黑色底就是容器。
3. **通用信号波 / 弧形波纹 / 雷达圈。** 「直播」最廉价的符号，品类里几十家在挤。
4. **四个色块 / 四色拼接代表四个平台。** 直接违反「不使用四家平台品牌色」，且四色在 48px 下糊成一团。
5. **网络节点 / 分子图**（中心圆 + 辐条 + 端点）。已明令禁止，且 48px 下退化成一只蜘蛛。
6. **任何细于 0.06 × 画布宽度的线**（108 单位下 < 6.5，48px 下 < 3.1px）。TV 上等于脏点，规范也已禁 1px 描边。
7. **渐变、外发光、彩色投影、毛玻璃、描边。** 规范五条禁令，图标不得例外；图标是最该守的一条。
8. **含字**：`L`、`LH`、`LiveHub`。理由见第 6 节。
9. **正圆红点。** 见第 5 节，这是本文件最硬的一条。
10. **超过 2 个实心块 + 1 道黑缝。** 超出 3 米特征预算，辨识度立刻掉一档。
11. **把 banner 的 8 列频道条缩进图标**，哪怕是「简化版」。它在图标尺度上不存在。
12. **第 4 种灰。** 图标里只允许 #000000 / #FFFFFF / #FF453A。banner 那套冷灰 #96969B 不进图标。

## 5. 红色在图标里的角色（本文件最难的一节）

**张力是什么**：规范写「强调色只出现在 LIVE 圆点、播放进度、进入直播间主按钮，不用于标题、标签、导航」。图标既不在这条白名单里，也不是状态。照字面读，图标不该有红。

**裁决：保留红色，把形状从「圆点」换成「徽章」，并把授权写死。**

理由是：那条白名单管的是**界面元素**（文字、容器、导航），而图标是**品牌标记**，跟字标同一类。而字标已经在用红了，`Hub` 三个字母就是 #FF453A。所以真实规则不是「红只给状态」，而是：

> **红色在本品牌有三个合法去处：状态（圆点）、字标（Hub）、图标（徽章）。除此之外一律不给。**

三者互不侵占，因为造型、位置、尺寸三样都不同：

| 用途 | 造型 | 位置 | 尺寸 | 语义 |
| --- | --- | --- | --- | --- |
| 状态 | **正圆** Ø10–12px | 行内、徽标内、播放页状态 | 小 | 这一路直播正在播 |
| 字标 | 字形 `Hub` | 词尾右端 | 随字号 | 品牌名的一半 |
| **图标** | **圆角条，≥2:1** | 三角右上肩，右缘对齐顶点 | 约 6.0px 高 @48px | 这是直播产品（类别判断） |

**为什么不会破坏「红色 = 在播」**：约束语义的从来不是颜色，是**形状 + 上下文**。界面上用户看到的红永远是圆的、永远贴着一个词或一个数字；图标里的红永远是条、永远不挨着任何词。两套造型在 48px 下已经不同（正圆 1:1 vs 长条 2.2:1），不需要用户学习。这条规则把红色语义从颜色层挪到造型层，语义反而更结实。

**并且图标里的红没有说谎**：它复刻的是 `.card__live`（红徽章压在封面右上角）在每张卡片上干的事。卡片上的红说「这张卡在播」，图标上的红说「这个 App 干的就是在播的活」。同一句式，从单张卡放大到整个产品，不是新语义。

**两条硬授权，请写进规范**：① 图标里红色构件**有且只有一个**，且必须是圆角条，宽高比 ≥ 2:1；② 图标红色墨量 **≤ 画布面积的 2%**（本方案实测 1.39%，约为白色墨量的五分之一）。超出即违规，不讨论。

**同帧出现两红时的准入条件**〔v1.2 · 回应 UI Designer 落地提问〕

上面那条「有且只有一个」管的是**图标内部**，不是整帧。同一帧里允许两处红同时在场，但必须过三道闸，**全部可测，不靠眼睛判断**：

1. **主从墨量差 ≥ 4×**：字标红墨量 ÷ 图标红墨量 ≥ 4。开屏实测 1 255 vs 8 719 = **6.95×**，通过；banner 实测约 **19×**，通过。为什么是 4 倍：面积 4× ≈ 线性尺寸 2×，而 2 倍是「主从可读」的最小可靠阈值，与 §1 那条 2 弧分/特征的算法同源 —— 低于 2 倍，两个红会被读成并列，而不是"一个主人加一个记号"。
2. **不同形同类**：两红不得是同一造型。字标红是字形，图标红是 2.22:1 圆角条，天然分离；若有人在字标旁再画一个红圆角条，即违规。
3. **不并排同高**：见 §6 与 §7.8，横排等高同基线一律禁止。开屏是上下结构、垂直不重叠、间隙 64，通过。

**降级触发线**：任何格式若让图标红墨量涨到字标红的 1/4 以上（不足 4× 差），该格式必须把徽章改为白色或整枚图标走 monochrome，只留字标红。**给出的是判据不是品味**，下一个格式自己算一遍就知道，不用回头问。

## 6. 字标与图标的关系 / 开屏

**图标是否含字：不含。四条理由，任一条都够。**
1. 48px 下「LiveHub」七个字母每个约 4px 宽，在 3 米外是七个小黑点。
2. 图像一旦内嵌字形，字体资产（Inter，自托管 `InterVariable.woff2`）就被焊死进图标，换字要重画图标。
3. 自适应图标在 Ø66 之外会被蒙版裁掉，字必然被切头去尾。
4. `android:label="LiveHub"` 本来就在同一个桌面格子里显示，图标里再写一遍是同屏两次同一个名字。

**开屏怎么共处：一处只给一个。** 〔v1.1 · 2026-10-29 · 主理人裁决补充〕

原条款写的是「图标与字标永不同框」。v1.1 把它收窄为**两条可执行的硬约束**，因为要防的从来不是「同框」这个动作本身，而是同框的两种具体形态：

1. **永不并排同高**：横向并列、等高、同基线，一律禁止。
2. **永不同时入场**：时间轴上接力，图标 0–340ms 到位，字标 340–600ms 才起，**零交叠**。

理由：并排同高会被读成两个并列主体，主导权不明；同时入场会让两个主体在 200ms 内互相争抢注意力。竖向错时接力则任一时刻**只有一个主体处于运动状态**，字标始终是最后落定的那个，主导权不丢。所以**竖向 lockup（图标在上、字标在下）+ 错时接力是允许的**，它不违反原条款，而是原条款的唯一合法解法。

各格式的落法：
- **Android 12+ 系统开屏**：SplashScreen API 在 `windowBackground` 上强制画 launcher icon，出不了字标。第一帧只有图标，没有字。
- **应用内开屏（竖向 lockup）**：图标在上、字标在下，按上述第 2 条错时接力。**这是应用内唯一允许两者同框的场合。**
- **应用内常规界面（开屏之后）**：只有字标（顶栏 30px / 600），不出现图标。
- **TV banner（320×180）**：唯一允许两者同框的**静态**格式，规则是**字标主导**：字标是主角，图形构件只能作为从属出现，**不得与字标等高并列**（即上述第 1 条）。

**谁主谁次，一句话**：字标是主，图标是门牌。门牌只负责「这家店在这儿」，招牌才负责「这家店叫什么」。**开屏时门牌先亮、招牌后落，顺序不能反。**

**连带的 banner 裁决（只给结论，改法留给下一阶段）**：banner 那组 8 列等高频道条应当随本裁决退役。三条硬伤：① 8 列对应不上 4 个平台；② 全部等高，零信息；③ 冷灰 #96969B 与规范的 #000000 / 暖黑 #0A0807 都不属同一套色系。但 banner 不是本轮范围，本轮不动。

## 7. 品牌一致性规则（给 UI Designer 与前端执行）

1. **颜色只有三个值**：底 `#000000`、白 `#FFFFFF`、红 `#FF453A`。出现第 4 个值（含任何灰、任何 alpha）即违规。现状图标底色 `#0C0C0E` **必须改回 #000000**：图标活在 OS 里不活在应用里；纯黑对白 21:1 是规范自己写下的数；且底色一旦不等于应用底色，系统开屏时那块黑方块会露出一道边，等于一条被规范明令禁止的「描边」。
2. **禁止正圆红点**。红色构件必须是宽高比 ≥ 2:1 的圆角条，全图只有一个。正圆红点是 `.livedot` 的专属造型，不得复用。
3. **徽章右缘与三角顶点 x 严格相等**，误差 0。这是本标记唯一可主张的独家细节，也是它不像「随手拼的播放键」的唯一原因。改这一条，母题即失效。
4. **那道黑缝 ≥ 0.08 × 三角高，不可省略**。它同时干三件事：区分两个块、保证 monochrome 层不粘连、维持规范「靠明度分界、不用描边」的做法。**这道缝不是留白，是构件。**
   〔v1.3〕**门槛用名义值卡，不要用实测值卡。** 名义值（4.217 = 0.088H，量到 bbox 角那个虚点）**恒 ≤** 实体间距，因为圆角只会把材料从角上削掉，物理上不可能把它推向斜边。所以名义值是最小值，拿它卡 0.08H 只会更严，不可能放过违规。渲染后量到的实体间距恒为名义值的 **1.37–1.43 倍**：48 档 4.24 / 72 档 5.94 / 96 档 7.64 / 144 档 11.88 / 192 档 16.13。**两种误判要堵死**：① 按「缝 ≥3px」算出 48 档 3.10 就以为踩线去动三角 —— 3.10 是名义值，本来就在限内；② 实测到 4.24 就以为画宽了回头压徽章 —— 4.24 才是实体间距。这条缝在任何一档都有 37% 以上余量，它从来不是风险项。
5. **圆角只有一档继承**：徽章用全圆（半径 = 高度一半，对应 `--r-pill`）；三角是尖角，**不圆角**。刻意不引用 `CardRadius = 20.dp`（20dp 是「装内容」的圆角，图标是「供识别」的标记，两者不是同类），也不引用 `SheetRadius = 28.dp`。图标里不出现 20 / 28 这两个数。
6. **不要自己烘圆角**。现有满出血方角的做法是对的（圆角交给 launcher 蒙版），只是底色错了。必须补齐 `mipmap-anydpi-v26` 三层（background / foreground / monochrome），现状一层都没有，Android 13 主题图标会直接缺失。
7. **尺寸按视口算，不按图层算**。三角高 = 72 视口高的 67%、宽 51%；现状是画布高的 45%、宽的 36%（相对视口还更低），**小了一倍以上**。这是现状图标看着「发虚、没重量」的唯一原因。
8. **一处只给一个**〔v1.1 修订〕：任一时刻只允许一个主体处于运动状态。图标与字标**不得并排同高**（横向并列、等高、同基线），**不得同时入场**（接力窗口零交叠）。落地：系统开屏只有图标；应用内开屏用竖向 lockup 错时接力，是唯一允许同框的场合；常规界面只有字标；banner 字标主导且不得与字标等高并列。
9. **加缝只能「加宽」三角，不能「收窄」**〔v1.2〕。徽章左端的圆弧压在斜边上方，而斜边绕**固定不动的顶点**摆动：三角底边右移（收窄）→ 斜边变陡 → 在同一 x 上抬得更高 → **缝反而变小**。实测名义缝（48 档，徽章左缘 x=23）：底边 11 → 3.10；11.5 → 2.94；10.5 → 3.26。方向与实体间距一致（实体恒为名义的 1.37–1.43 倍，单调同向）。这条杠杆很钝（+0.5 只换 +0.16），更有效的顺序是：徽章左缘右移（+0.54/px，但宽高比会压向 2.00）、徽章整体上移（+0.84/px，但会改掉 0.06H 的肩部比例）。**凡凭直觉去「收三角求缝隙」，一律驳回。**

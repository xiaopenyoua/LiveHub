# 弹幕「有限重连」夹具

一个**桌面 JVM** 测试，用本地可控的 WebSocket 服务端反复掐断连接，验证
`core/danmaku/` 里那套「有限重连 + 只提示一次」的策略在真实代码上确实成立。

它不是单元测试，也不是 Gradle 任务。**不进 app 模块、不参与 `assembleDebug`**，
用 Gradle 缓存里已有的 kotlinc 与依赖 jar 直接编译运行，全程不联网。

## 为什么需要它

重连逻辑最典型的坏法不是「连不上」，而是**错误地在不该说话的时候说话**：
一次 200ms 抖动就在用户屏幕上闪一句「弹幕连接已断开，重新开关弹幕可恢复」，
比完全不提示更伤信任。这种毛病真机上不可复现（网络抖动不可控）、代码审查看不出来
（判据分散在几个 `if` 里），只能靠本地掐断。

现在这三件事各有一个专门的用例守着：

1. 重连过程**不发任何事件**，`Connected` 每次 `collect` 只见一次；
2. 一次中断**只提示一次** `System`，且「距上次连上不足 `ANNOUNCE_AFTER_MS`」时**完全不提示**；
3. 到 `MAX_RETRY` 才发 `Failed` 收尾，且**上限分支只发 `Failed`**，不先说「已断开」。

外加第四条，它走的是完全另一条代码路径（`collect` 被取消、流被丢弃、`stream()` 重新调用）：

4. **关掉弹幕再打开**能恢复：取消不发 `Failed` 也不发 `System`，重新 `collect` 有独立的一次
   `Connected`，且重连计数从 0 起算而不是接着上一次（`S5`）。

## 怎么跑

```bash
cd android/tools/danmaku-reconnect-test
./run.sh              # 全部 11 组 / 84 条断言，约 3 分钟
./run.sh douyu        # 只跑斗鱼（S1/S4/S2/S3 + 斗鱼那两组 S5）
./run.sh huya         # 只跑虎牙（S1/S4/S3 + 虎牙那两组 S5）
./run.sh S5           # 只跑「关→开」四组（斗鱼、虎牙各含一组脏计数）
./run.sh S2           # 按标题子串过滤，任意字符串都行
```

前置条件：

- JDK 17+（用 `java` 直接跑 kotlin-compiler-embeddable，不需要装 kotlinc）；
- **本仓库至少成功构建过一次**（`./gradlew :app:compileDebugKotlin`），
  因为所需的 okhttp / okio / coroutines / json / kotlin 编译器 jar 都从
  `~/.gradle/caches/modules-2/files-2.1` 里取；缓存换过位置就设 `GRADLE_CACHE=<path>`；
- `patch`（macOS 自带）。

退出码 0 = 全部断言通过，1 = 有失败。输出是一份带时间戳的流水，
`t=` 是相对本组用例开始的毫秒数，`client` 行是真正从 `Flow` 里收到的 `DanmakuEvent`。

## 唯一允许的源码改动

**仓库里 `app/src/main/java/.../core/danmaku/` 的源码零改动，没有留任何 hook。**

`run.sh` 每次都把 `core/{danmaku,net,model}` 拷到 `build/gen/`，然后对**副本**打
`patches/endpoints.patch`。补丁只做一件性质相同的事：**把外部世界换成本地可控输入**。

| 覆盖点 | 换掉什么 | 为什么必须换 |
|---|---|---|
| `douyu.ws` | 斗鱼 WS 端点 | 要能在任意毫秒掐断，只能指向本地服务端 |
| `huya.ws` | 虎牙 WS 端点 | 同上 |
| `huya.room` | `resolve()` 里的 HTTP 查房间 | 虎牙**每次重连前**都要真调一次 `mp.huya.com` 换 topSid。不换掉的话这组用例会变成「网络测试」，还会依赖某个主播是否正在播——那就不是回归资产了 |

三个属性**不设时值/行为与仓库版本完全一致**（都带默认值兜底），所以补丁本身不会
改变被测逻辑。它只作用于 `build/gen/`，每次 `run.sh` 都重新生成。

`run.sh` 里先 `patch --dry-run`：**如果生产源码动过 `WS_URL` 或 `resolve()` 开头那几行，
补丁会打不上并直接报错**，提示你同步更新补丁——避免悄悄测一个过时的副本。

## 用例表

| 用例 | 场景 | 守的是 |
|---|---|---|
| `S1 抖动恢复` | 连上后 200~700ms 掐断 4 次（优雅 close 与 RST 交替），每次 1s 后重连成功 | `attempt` 连上即清零、`connectedSent` 只发一次 `Connected`、零 `System` |
| `S4 三秒阈值` | 连上 → 300ms 被掐 → 下次重连被拒（此刻距上次成功仅 1.3s）→ 再下次成功 | `ANNOUNCE_AFTER_MS = 3000`。**把这个常量删掉或改 0，此组必红** |
| `S2 真断不复`（仅斗鱼） | 连上 5s 后 RST 并关闭监听，之后永远连不上 | `MAX_RETRY`、`announced` 只置一次、上限判断在提示之前 |
| `S3 从未连上` | 端口没人监听（一次都没连上过） | `everUp` 守卫：没连上过就不许说「已断开」；上限分支只发 `Failed` |
| `S5 关→开` | 同一实例：`collect` #1 收到 `Connected`+`Chat` → 用户 `cancel()` → **服务端随后**才把旧连接收掉 → 再 `collect` 一次 | 取消路径不发 `Failed`/`System`；第二次 `collect` 有自己的一条 `Connected` 且能收到新弹幕；一条被丢弃的旧连接晚一步关掉不污染新 `collect` |
| `S5 关→开·脏计数` | 在**退避窗口里** cancel（此刻 `attempt` 已涨到 1），重新 `collect` 后前两次重连被拒、第三次成功 | 重连计数不许跨 `collect` 共享。干净 → 退避 1s,2s，首条弹幕 ≈3.1s；若计数串了 → 2s,4s ≈6.1s。判别上限 4800ms |

覆盖：斗鱼 4 组、虎牙 3 组（`S1`/`S4`/`S3`），加上 `S5` 四组（斗鱼、虎牙各「基础 + 脏计数」）。
虎牙没跑 `S2`：它的 `S3` 已经覆盖「上限只发 Failed」，`S1`/`S4` 覆盖「只提示一次 / 阈值」，
`S2` 的唯一增量是「`announced` 只置一次」，而它的骨架与斗鱼逐行同构。

`S5` 两组分开写不是重复：基础组验「正常关→开」，脏计数组验「**在重连过程中**关→开」——
后者才是用户真正会做的那次操作（看到弹幕不刷新、连不上，就先关掉再打开），而它恰好是
`attempt`/`announced` 最容易被顺手挪成实例字段的地方。脏计数这组的断言语义是
「退避序列的**起点**必须是 0」，它比的不是某个时间点，而是「两次失败之间隔了多久」。

那组还有一份**直接证据**在日志里：`reconnect #N` 打的是 `attempt + 1`，所以干净计数下
整场应当出现两条 `reconnect #1`（`collect` #1 一条、`collect` #2 一条）。如果第二条变成
`reconnect #2`，就是计数跨 `collect` 串了。3142ms 只是把这个事实换成一个能自动判的数字。

**哔哩故意不覆盖**：它的重连逻辑与斗鱼同构（同一套 `attempt`/`announced`/`upAt`），
独有的部分只有 `auth reply` 和 zlib 压缩，而这两块已经被真机验证过（设备上看到的中文
弹幕就是走这条路的）。为了验证一段已被验证过的代码去写 zlib 夹具，是把测试成本花在
最不可能坏的地方。

## 想改就改，但这三类改动会让断言失效

1. **改了 `MAX_RETRY` / `ANNOUNCE_AFTER_MS`**：
   `S2` 的 `systemAt = 3000..12000` 与 `systemToFailedGap`、`S3` 的 `durationMs`
   都是按 `1+2+4+8+16s` 推的，改参数要一起改期望，否则会红——**红得有道理**，别急着放宽。
2. **改了 `WS_URL` 常量或 `resolve()` 开头几行**：更新 `patches/endpoints.patch`
   （`run.sh` 的 dry-run 会提醒你）。
3. **改了 `backoff()` 的底数或上限**：`S5 关→开·脏计数` 的 4800ms 判别阈值是按
   「1s,2s 恢复 ≈3.1s / 2s,4s 恢复 ≈6.1s」这两个实测值卡出来的。底数变小会让两者都塞进
   阈值内、判别失效（**假绿**，比红更糟），届时必须重新量一次真实恢复耗时再定阈值。

## 它验不了什么

- **真机能连上**：虎牙/斗鱼的真实房间握手、注册组、心跳、解码，这组夹具用的是自己造的
  合法包，只证明「解码器能吃下这个形状」，不证明「服务端真的这么回」。那件事靠真机。
- **哔哩的任何行为**：见上。
- **重连后会漏掉多少条弹幕**：夹具的弹幕条数是脚本写死的，不反映真实密度。
- **两处同时 `collect` 同一个实例**：`S5` 是**串行**的（先 `cancel` 再 `collect`），也就是
  UI 上「关掉弹幕、再打开」这一种。如果哪天有两个界面同时收同一实例的 `stream()`，
  行为不在本夹具覆盖范围内。

# LiveHub 测试方案

> 版本：应用 `1.0.0` · 设计定稿 `design/v1.0.0/`
> 配套清单：`android/docs/功能清单.md`（功能 ID 以那份为准）
> 目标设备：Android TV AVD `googletv_api36` / 1920×1080 / density 320；真机验收同口径
> 这份方案的重点不是「把按钮点一遍」，而是**证明直播能长时间稳定地播下去**：不同平台、不同画质、不同线路，各跑满 30 分钟，并留下可复算的证据。

## 1. 要回答的七个问题

| # | 问题 | 答完的形态 |
|---|---|---|
| T1 | 四家平台在当前网络下各能播到什么程度 | 每平台一行：能否进房 / 首帧耗时 / 真实分辨率与码率 / 断流或 EOF 时刻 / 失败文案是否归责正确 |
| T2 | 播放页三态（在播 / 断流但活着 / 彻底失败）界面是否可区分 | 三态截图 + 每态可聚焦控件枚举 |
| T3 | 不同清晰度是否真的改变取流，且显示诚实 | 每个档位记录「请求值 / 实际签发值 / 屏幕显示值」，三者对得上 |
| T4 | 不同线路是否都能起播，坏线路是否能被识别并换掉 | 每条线路：首帧耗时 / 是否持续 / 失败码 / 是否自动换线且不死循环 |
| T5 | 30 分钟连续播放的稳定性形态 | 每平台：存活率 / 在动区间数 / 最长静止 / 重缓冲次数与时长 / 首帧后停住次数 / FATAL 与 ANR |
| T6 | 设置项是否「改 → 落盘 → 生效」三段齐全 | 每个真落盘项逐项三段证据；灰置项不得进入焦点链 |
| T7 | 焦点系统有没有第二类错位 | 五个屏每个可聚焦元素都到达过；边界不动是允许的，非边界卡住是缺陷 |

## 2. 环境、构建与启动

### 2.1 构建与安装

```bash
cd android
./gradlew :app:testDebugUnitTest --console=plain   # 单测（Net 错误码、斗鱼形状、虎牙重试、数据层）
./gradlew :app:assembleDebug --console=plain
/Users/wangq/Library/Android/sdk/platform-tools/adb install -r app/build/outputs/apk/debug/app-debug.apk
```

### 2.2 启动

```bash
ADB=/Users/wangq/Library/Android/sdk/platform-tools/adb

# 正常启动（走开屏）
$ADB shell am force-stop com.livehub.tv
$ADB shell am start -n com.livehub.tv/.MainActivity

# 测试直达（仅 debug 包）：平台 + 房间号 / web_rid；可同时指定清晰度
$ADB shell am start -n com.livehub.tv/.MainActivity \
  --es debug_room bilibili:545068 --es debug_quality 250

# 平台 key：bilibili / douyu / huya / douyin
```

`debug_room` 只在 `FLAG_DEBUGGABLE` 为真时生效；release 包即使传入也忽略。

### 2.3 遥控器驱动

不用 `uiautomator dump`（本环境会退化并吞键）。只用：

```bash
$ADB shell input keyevent KEYCODE_DPAD_DOWN
$ADB shell input keyevent KEYCODE_DPAD_CENTER   # OK
$ADB shell input keyevent KEYCODE_BACK
```

截图：

```bash
$ADB exec-out screencap -p > /tmp/x.png          # 一次性前台执行
```

长时间跑：`python3 android/tools/soak.py --tag <tag> --seconds 1800 --shot-every 60 --out /tmp/livehub-soak`

## 3. 判据与证据规范

### 3.1 结论只有五种

| 结论 | 条件 |
|---|---|
| **PASS** | 期望现象以指定证据出现；同一结论执行 2 次（中间 force-stop）一致 |
| **FAIL** | 期望缺席/矛盾；有截图或 logcat；同进程重试 1 次仍缺席；排除前置失败 |
| **NV-A** | 本环境没有任何手段观测（落到 §9 某一条并写「需要补什么」） |
| **NV-B** | 只看到 1 次或 0 次，重试不到；写明证据与差异 |
| **NV-C** | 证据存在但读不出结论（糊、遮挡、时序错过）；保留原始证据 |

### 3.2 六条边界

1. 只看到一次、复现不了 → 一律 NV-B，禁止升 FAIL。
2. 代码证据可以把 NV 升 FAIL，**不能**把任何东西升 PASS。
3. 「进了房但没画面」≠「起播失败」：分开记 UI / 画面 / 入向三件事。
4. 一次 PASS 不算 PASS。
5. 前置失败不许计成 App 失败（进错屏、焦点没到、按键被吞）。
6. 同一功能点不同平台结论不同 → 按平台分行记，不许合并。

### 3.3 本环境的测量硬约束（违反则该轮数据作废）

| # | 约束 | 后果 |
|---|---|---|
| 1 | 禁止 `uiautomator dump` | 会退化到 100s/次并吞按键 |
| 2 | 截图只约束「谁收 stdout」：一次 `exec-out` + 重定向到文件 + 前台 | adbd 持管道会让命令永不返回（exit 137） |
| 3 | 判「画面在动」只能靠**定时截图 + 相邻帧像素差分**；`dumpsys SurfaceFlinger --latency` 不采信 | 本 AVD 恒返回一行刷新率 |
| 4 | 任何内存采样前先做静置对照；优先读 `/proc/<pid>/status` 的 VmRSS，不用 `dumpsys meminfo` | `meminfo` 会强制 full GC，读数与 GC 次数都是伪影 |
| 5 | 采样器放设备内或宿主侧低频调用，不要在宿主每 30s 起一次 adb | 本机 adbd 已证明会掉线 |
| 6 | 禁止 `adb kill-server` / `adb reboot` | adbd 恢复要 1–5 分钟 |
| 7 | 判「在播」不许用静态统计量（非黑占比、平均亮度）；只认时间轴差分或应用遥测 | 403 页的非黑占比会落在真在播区间内，没有分辨力 |
| 8 | 浸泡每一轮必须记录**线号**与**清晰度** | 零按键浸泡只跑第一条线路；不记线号会把「只测了一条 CDN」当成「整个平台都测了」 |

### 3.4 证据命名

```
<日期>-<平台>-<房间>-<档位>-<线号>-<状态>.png
例：20261030-huya-1995-chaoqing-line1-firstframe.png
```

每轮浸泡在 `meta.txt` 里写：开始时间、时长、截图间隔、启动时线号/档位；`samples.csv` 每行一个采样点；`player.log` 收 `LiveHubPlayer`、`AndroidRuntime`、`ActivityManager`、`LiveHubFocus`。

## 5. 直播稳定性专项（本方案的核心）

### 5.1 覆盖矩阵

| 维度 | 哔哩哔哩 | 斗鱼 | 虎牙 | 抖音 |
|---|---|---|---|---|
| 主房间 | `545068`（在播游戏） | `252140` / `317422` | `1995` / `998` | `59288147052`（已知详情失败）或当晚在播 web_rid |
| 线路 | 6 条（4 HLS + 2 FLV）全切 | 1 条（主） | 4 条（1 HLS + 3 FLV）全切 | 8 条（4 FLV + 4 HLS）抽样 |
| 清晰度 | 自动 / 150 / 250 / 400（记录实际签发） | 预览（唯一档） | 当前档（接口只给一档） | ORIGION / FULL_HD1 / HD1 / SD（取实际存在的 key） |
| 30 分钟浸泡 | 1 轮 | 1 轮 | 1 轮 | 抖音已可起播，补 1 轮 |
| 起播/断流/重连 | 必须 | 必须 | 必须 | 必须（如可播） |

**每轮浸泡前**：记录启动线号与清晰度；关弹幕（弹幕会污染「画面是否在动」的差分）。
**每轮浸泡后**：`samples.csv` + `shots/` + `player.log` + `wc -l player.log`（<1000 行判该轮日志不可用）。

### 5.2 三个数 + 五条判据

三个数：

- `m` = 在动区间占比（相邻截图、`ROI-VIDEO=(0,152,1920,860)`、luma 差 ≥1）
- `A` = 平均入向 kbps（`/proc/net/dev` 全设备口径，注意页面字节冒充视频）
- `S` = 最长连续静止秒数

按顺序匹配，先命中先定：

| 顺序 | 判据 | 条件 | 结论 |
|---|---|---|---|
| ① | C1 崩溃型 | `pidof` 为 0，或 logcat `FATAL EXCEPTION` / `ANR in` | 崩溃（FAIL，最高优先级） |
| ② | C3 无有效流 | `m` 可算且 = 0、`A < 100`、进程存活 100% | 无有效流（FAIL，需再分型） |
| ③ | C2 断流型 | 存在区间 k，之后所有区间 <0.2%，之前至少 1 个 ≥5%，后期均值 < 起播期 ×5% | 断流（FAIL，附窗口） |
| ④ | C5 不稳定 | 不满足以上、也不满足 C4（`m` 落在 (0,0.9)，或 `m=0` 但 `A≥100`） | 不稳定（FAIL，附 m/S/A） |
| ⑤ | C4 正常 | `m ≥ 0.90` 且 `A ≥ 300` 且 `S < 120` 且 FATAL=0 且 ANR=0 | 稳（PASS） |

**补充判据（2026-10-30 新增，必须一起看）**：

- **首帧**：`first frame rendered ... latencyMs ≤ 12000`。超过 12s 说明起播兜底应已触发。
- **静默停住**：出现 `stalled` 且屏上 5s 内没有任何原因文案 → FAIL；有文案/自动换线 → 记录。看门狗读 `renderedOutputBufferCount`（每秒轮询），不读 `currentPosition`（直播 HLS 可能恒 0）。
- **EOF 恢复**：每次 `STATE_ENDED` 后 30s 内必须出现新的 `first frame` 或明确的终态文案；否则 FAIL。
- **重连频率**：记录 `STATE_ENDED` 次数与每次播放时长。虎牙 FLV 在本环境可能每 4–9s EOF 一次，这是 CDN 行为，不是应用崩溃；但**必须看到自动重连且画面恢复**。
- **切线路不死循环**：不能出现「正在换线路…」1→2→3→4→1 反复闪；翻 PASS 的标志是「停在一个终态并说清原因」或「找到一条能持续播的线路」。

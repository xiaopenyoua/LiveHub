# 06 · 四平台接口实测记录

> 复现方式：`android/tools/probe-sites.sh`（可单独跑某一家：`./tools/probe-sites.sh huya`）
> 判定标准：HTTP 200 **且** 响应里出现「只有成功才会有的字段」。只看 200 不算数——哔哩风控时返回的是 HTTP 200 + `{"code":-352}`，抖音参数错了也是 HTTP 200 + `{"data":{"message":"Request params error"}}`。

本文只写**实测通过、可直接照着写代码**的东西。抓包反推的字段表、签名算法这类没验证过的内容在 `docs/逆向分析.md` 里，两处不重复。

> **硬规则：`android/tools/probe-sites.sh` 与 `core/site/*Site.kt` 必须用同一套判据，改一处必须改另一处。**
> 理由不是洁癖：**脚本假绿比脚本报错危险**——脚本报错我们会去查，脚本假绿我们会以为没事。判据一旦两边漂移，**漂移的那一侧永远是脚本**（因为没人天天读它），于是监督机制先烂掉。
> 配套的验证手法也记在这里：**验解析器要用「不该命中的输入」，不是「该命中的输入」**。抖音那条「往前找最近的 `roomId`」就是这样撞出来的——正向用例全是短路径，只有「找不到」才会走到最坏分支，逻辑错和性能坑（同一条写法在 879KB 页面上卡死 >12s）都藏在那儿。

### 1.1 三个坑（都踩过）

**坑一：`second/getList` 和 `getListByArea` 已经不能用了。**
这两个是各家教程里最常写的首页接口，现在一律返回 `{"code":-352}`。加 `buvid3` Cookie 也没用——我实测过，请求头带上从 `x/frontend/finger/spi` 拿的真 buvid3，仍然是 -352。真正的门槛是 **wbi 签名**（`w_rid` + `wts`）。

首页改用 `room/v1/room/get_user_recommend`，它还是免签的，一次给 30 条，字段够用：

```
roomid, title, uname, face, user_cover, system_cover,
areaName, online, uid, watched_show.text_small
```

> 备注：`nav` 接口（`https://api.bilibili.com/x/web-interface/nav`）未登录返回 `code:-101`，但 `data.wbi_img.{img_url,sub_url}` 里**仍然给了 img_key / sub_key**。真需要上 wbi 时从这里取密钥，别去猜。

**坑二：`getDanmuInfo` 也上了 wbi。**
未登录直接 `-352`，弹幕连不上。救回来的是老接口 `room/v1/Danmu/getConf`——免签，返回结构几乎一样（`token` + `host_server_list`，`wss_port` 都是 443）。

`BilibiliDanmaku.kt` 已按「getConf 优先 → getDanmuInfo 兜底」改过。getDanmuInfo 想救活得算 `w_rid`，约 40 行，只为兜底不值得；哪天 getConf 也挂了再说。

**坑三：`current_qn` 不一定等于你请求的 `qn`——但"未登录"不是原因。**

请求写 `qn=10000`，返回的 `current_qn` 可能只有 250 或 150。**这条原来是「未登录时被压到 250」，已撤回**：§1.3.1 的匿名扫描里，匿名直接拿到 10000 的房间确实存在，拿到 150 / 250 的也确实存在。能站住的说法是**签发哪一档由房间与推流端决定，登录态不是决定因素**——**这里不写任何比例，理由在 §1.3.1（同一个抽样源隔一轮就换一批房间）**。

处理方式不变——**如实显示 `current_qn` 对应的档位**（250 = 超清 720P），别硬编码「原画」，也别替平台宣布"未登录上限"。250 既不是 1080P、也不是「高清」，两个方向各错过一次，见下表那段。

质量名映射：`10000 → 原画` / `400 → 蓝光` / `250 → 超清` / `150 → 高清`。

> **这张表是判据，不是文案，而且它现在有出处了。** 全仓唯一一份 qn → 名字的表是 `core/model/Quality.kt` 的 `bilibiliQuality(qn)`（真调用一处：`BilibiliSite.kt` 里搜 `bilibiliQuality(c.optInt("current_qn"`；`ui/` 侧**代码命中 0**，`Cards.kt` 里那 2 处都在 KDoc 注释里），数值逐条取自平台在取流响应里返回的 `playurl_info.playurl.g_qn_desc`。**读这张表时要把分辨率一起读**：
>
> | qn | 平台 `desc` | 平台 `brief_desc` | 会不会真的出现 |
> | --- | --- | --- | --- |
> | 80 | 流畅 | — | `g_qn_desc` 里有，未实测到被签发，**本节不收** |
> | 150 | 高清 | 480P | 免费/未登录的常见档 |
> | 250 | 超清 | **720P** | 未登录房间里出现过；**它不是"未登录的上限"**（§1.3.1） |
> | 400 | 蓝光 | 1080P | 手里有 400 的 `current_qn` 样本 |
> | 10000 | 原画 | 1080P | 登录后，**被压档的那类房间**才直接给（§1.3）；匿名也经常直接给（§1.3.1） |
> | 15000 | 2K 极清 | 2K | 只出现在 `accept_qn` 里，未签发 |
>
> **这里踩过两次，方向相反，两次都值得记：** ① 旧 `qnName()` 把 `150` 写成「流畅」、`250` 写成「高清」，**低报一档**，连带 `qualityRank("高清")` 把 250 判成 150、弹一条服务端根本没压档的假降档提示；② `ui/components/Cards.kt` 曾写着 `250 → "超清 1080P"`，**高报一档**，而 `1080P` 在全仓找不到出处（`400`/`10000` 才是 1080P）——这一处**2026-10-29 已改成 `超清 720P`**；但同一句话在 `PlayerScreen.kt` 里搜 `未登录，最高 1080P` 那一行 以 `"未登录，最高 1080P"` 的形态**还活着，而且已经在产物里**：`app-debug.apk`（md5 `c195a6605a9d9a4cf28b3544731e901c`，14 个 dex）的字符串表里这条命中 **1 次**，在 `classes4.dex`。**源码里还有一行**和**装到电视上的包里还有这句话**是两件事，这一处是后者。**低报和高报都是谎，区别只是哪个方向更容易被当场发现。** 判据永远是那个字段，不是"看着像"。
>
> 留在 `ui` 的那份表归 frontend 改，验收**三条**写在 `04` §7.1 的 ⚠️ 框里（入参不再是 `String` + `bilibiliQuality()` 调用点 ≥ 2 + 同档同分辨率）。**另有一条只对 `qualityRank` 的护栏**：它必须把 `qn <= 0` 判成 `-1`，否则斗鱼/虎牙/抖音的 `qn` 恒 0 会让 `0 in 0 until w` 成立，**每个房间都弹一句「平台只给到 未知画质」**——判法是看字节码里有没有 `ifle`，不是读代码。**别按感觉改，也别在这里顺手补没验过的档**——补一格错的，会让下游整条判据跟着错。

取流参数：`protocol=0,1&format=0,1,2&codec=0,1&qn=10000&platform=web&ptype=8&dolby=5&panorama=1`，
地址在 `data.playurl_info.playurl.stream[].format[].codec[].url_info[]`，每条 `url_info` 有自己的 `host + base_url + extra`，**拼起来才是完整地址**，且每条线路的 `extra` 不同（别复用）。

> **取流时按 `format` 分桶，不要取第一条。** `protocol=0,1&format=0,1,2` 返回的第一个 `url_info` 是 **FLV**，它的字节头是 `FLV\x01` + `onMetaData`。先前把它当 m3u8 存下来做校验，看着「URL 通」其实是 FLV 内容——这就是拿到「通」却播不出来的典型假象。

### 1.3 登录前后到底差什么：`accept_qn` 不变，`current_qn` 变（2026-10-29）

方法：浏览器 profile 本来就登录着（账号 `暴打小人机`，`vipStatus=0` 非大会员），**在页面内**发两次同样的请求，只把 `credentials` 在 `'omit'` / `'include'` 之间切换，同房间同一刻对照。**全程没有读取任何 cookie/token**，所以这张表里没有一个字节是从浏览器存储里抄出来的。

| 房间 | 匿名 `current` | 登录 `current` | 匿名 `accept` | 登录 `accept` |
| --- | --- | --- | --- | --- |
| 6（即 `room_id=7734200`，§1.2 那个赛事房） | `[150,250]` | `[10000]` | `[150,250,400,10000,15000]` | 同左 |
| 21452505（§3 与 `05` §三 的实测房间） | `[250]` | `[10000]` | `[250,400,10000]` | 同左 |

**两列 `accept` 一字不差，是整张表最有用的一格**：平台**允许**你请求哪些档，登录前后完全相同。所以：

- **`accept_qn` 不能当"登录有没有收益"的判据**——它回答"允许什么"，不回答"给你什么"。拿它判，结论会是"四家登录都没用"。
- 判据只有 `current_qn`（实际签发那一档）：250 → 10000 才算收益。
- 「登录后解锁更高画质」这句话是**假的**：可选项一个都没多。
- **「登录后直接给原画」也不能整句说出去**：它只在**匿名被压档的那些房间**成立。下面 §1.3.1 的匿名扫描里**本来就有原画的房间确实存在，而且不缺**——对那些用户说这句，等于告诉他"你现在没有"，而他手里正拿着。能对外说的只有一句：**「登录后，被压档的房间直接给原画」。**
- **这张表是抽样，不是平台上限**：`匿名 current` 列的 `[150,250]` / `[250]` **只描述被抽到的这两个房间**，不构成"匿名最高多少"的规则（§1.3.1 已推翻）；`accept` 那两格也是按 codec 行取的，不是顶层字段（见下面口径）。

> **口径（已定稿，三版才对，前两版都是我猜的）**：`current` 是**按 codec 行去重后的 `current_qn` 集合**。它既不是"响应里的单个字段"（第一版写法），也不是"flv/ts 两条流各一档"（第二版写法，**错的**）。实测（2026-10-29，匿名 + `buvid3`，`qn=10000&platform=web&ptype=8`，房间 6）：
>
> ```
> format=0,1,2  codec=1(avc only)  →  flv 150 / ts 150 / fmp4 150   accept=[15000,10000,400,250,150]
> format=0,1,2  codec=0,1          →  avc 三行 150 / hevc 三行 250   hevc 的 accept=[15000,10000,400,250]（**没有 150**）
> ```
>
> **250 来自 hevc，不是来自另一条流。** `accept_qn` 同样挂在 codec 行上——取顶层会拿到 `None`（backend 第一版脚本就栽在这里，拿到 `None` 之后差点写成"平台没返回"）。
>
> **还有一件更麻烦的：`format` 集合本身会改签发值。** 同房间同一刻，只请求 `format=2`（fmp4）时那条 `current_qn=250`；`format=0,1,2` 一起请求时，同一条 fmp4 行是 `150`。`platform` / `ptype` 试过三个组合（`web/8`、`h5/8`、`web/1`）**都不影响**——这条可以排除，省得以后有人怀疑是 h5/web 差异（`05:73` 那条实测写的是 `platform=h5`，很容易把人往这个方向引）。
>
> **所以复算必须锁死四个量：`credentials` + `protocol` + `format` + `codec`。** 少锁一个，得到的是另一个数，而**两个数看上去都对**。把它写成 `current_qn = 250` 会让下一个人拿它和 `accept_qn` 做单值比较——**结论会变成"平台只接受一档"，而真值是"平台接受五档、只签发一档"**。同一个数，两种读法，两个相反的结论。

> **还有一处口径坑，同一个形状**：抖音 `resolution_name` 里写着「原画（ORIGION）」，但 `flv_pull_url` / `hls_pull_url_map` 里可能没有对应 key（§4.3）。**「列表里有」不等于「能要到」**——哔哩这里是 `accept_qn` vs `current_qn`，抖音那里是 `resolution_name` vs `pull_url_map`，同一个错误的两张脸。

### 1.3.1 匿名到底能不能拿到原画（**推翻了上面那条直觉**）

上表那张两房间对照会让人得出"未登录被压到 250"。**那个结论是错的**，因为它只有两个房间。

匿名扫描 **R1**（2026-10-29 早些；**只有 `buvid3`，无任何登录态**；`qn=10000&platform=web&ptype=8&protocol=0,1&format=0,1,2`；12 个活跃房间；**逐房间记录，一行一个房间号**）。**同一节下面还有一张 R3，两张表各自独立、不要合并成一个样本**：

**这张表一行一个房间号，但表下面不写"几个是 10000、几个是 250"。** 理由不是数字算错了（逐行数得出来），是**它只要能脱离这张表被引用，就已经在冒充分布**——下一轮的实测就是反证。`g_qn_desc` 把 10000 标成「原画」。被压档的那几个房间，`accept_qn` 里**同时有 250 和 10000**——**平台允许要原画，签发的却是 250**，这才是"压档"的真实形态，也是这件事唯一需要记住的机制（它比"压了多少个"稳，因为它逐房间可验）。

> **这张表能支持的只有两件事：① 存在性——匿名就能拿到原画的房间确实有，被压档的房间也确实有；② 这一轮发生了什么——一行一个房间号，逐行可复算。它不能支持任何比例。** 抽样源是「按在线人数排序的分区列表」（这句在 `Cards.kt` 的 `qualityLabel` KDoc 里，搜 `抽样源`；「同一天重扫就会变」那条在 `Quality.kt` 的 `bilibiliQuality` KDoc 第 3 条里，搜 `这里不许写比例`）——**而"会变"这件事不是推测，下一轮就验到了，见下面那块。**
>
> **算术也要自证一次：这张表是 12 行，不是 13 行。** 房间 6 与房间 21452505 属于 §1.3 那张两房间对照，**不在这 12 个里**；而且房间 6 的匿名 `current` 是集合 `[150,250]`（avc 150 / hevc 250），不是"150"。**「9 个原画 + 3 个 250 + 房间 6 是 150」加在一起会得到 13**——那是把两张表混算。本轮的 12 房间表内部自洽（9+3=12），**矛盾出在那句叙述，不在数据**。叙述里多出来的一格，比数据里少一行更难发现，因为**加法是判据，叙述不是**。**这两个数在这里只用来对账，不用来外推**——对完账它们就该消失，留在正文里只会被下一个引用的人当成结论。
>
> **R2（2026-10-29 稍晚；同一抽样源、同一请求参数、同样只有 `buvid3`）：11 个活跃房间，房间号与 R1 几乎不重合。但这一轮的房号丢了。** 扫描输出只进了终端，没落盘；**当时**查过 `/tmp`，8 个相关文件全是脚本、没有一个输出文件（`/tmp` 现已清，这一句是那一次的查证记录，不是一条还能去核的坐标）。**所以它只能作旁证，不能作表**——本节不给它补房号，也不写它的计数。**把记忆里的计数配上一组回忆出来的房号凑成一张表，能通过任何形式检查（行数对、房号在、合计对），唯一缺的是"真的发生过"**——这比"没有表"贵得多，因为读者无法证伪，只能选择信。**没落盘的实测等于没测**，这是本项目第二次栽在"证据没留下来"上（第一次是斗鱼两个样本的中间值变成了门限）。

> **R3 有三件 R1 证不了的事，都写在表里，不需要正文辩解**：① **12/12 `live=1`**——「那个 250 是因为没在播」这个最常见的解释当场被排掉；② `1967222776`（250）与 `31109886`（10000）**同 cookie、同四个参数**（`credentials` / `protocol` / `format` / `codec` 全锁死），两个房号都在表里，谁都能重跑；③ 断言的形状是**存在性 + 反例**，不是计数。
>
> **最硬的一条证据不是任何比率，是两张表能做集合运算：R1 ∩ R3 = ∅。** 12 + 12 = **24 个不同房号，零重合**——同脚本、同参数、同一天，两次扫描没有一个房间重复。这个 `0` 比任何比率都有用：**比率能被单独引用，交集不能**。摘一句「9/12」只要一句话，摘「交集为 0」必须把两张表一起搬走。
>
> **R3 还有一条只作观察、不作解释的**：拿 10000 的那 11 个房间，`accept_qn` 全是 `[10000]`；唯一那个 250 的房间是 `[10000, 400, 250]`。**这中间有没有因果，没做过实验，不写机制**——按"被解释过的 0 比没解释的 0 更危险"的同一条逻辑，没验过的机制比没有机制更贵。
>
> **原始输出未入库，也不留 `/tmp` 指针**（`/tmp` 已清）。**可复算的是那 12 个房号 + 上面那串完整参数**：同一天、同参数重扫，能独立得到「匿名房间里同时存在 250 与 10000」这个反例。**长期可复算的东西是房号和参数，不是那次运行的字节——把房号抄进正文，就已经把"可复算"这件事落地了。**
>
> **这里原来写的是「落盘在 `/tmp/qn_r3.txt`，`md5=0fd79f3f…`，841 字节」，撤掉了，理由值得记。** `md5` 指着一个 `/tmp` 文件，是**一个会继续存在、并指到空处的坐标**——比没有坐标更坏，因为它在读者眼里和「可复算」长得一模一样，而 `/tmp` 一清，那句话就从「可验证」变成「不可验证但看起来可验证」。**这和「行号指到别的东西上」是同一族，只是它指到的是什么都没有。**
>
> **「没落盘的实测等于没测」这句仍然成立，但它管的是另一件事**：它管的是「**写结论时不许引用没落盘的数**」（所以 R2 不给房号、不写计数），**不是「必须把文件存起来」**。存 `.txt` 只是把「当时那一次」存下来；那一次的证据价值已经由正文的房号 + 参数承担，而一份**平台数据快照**（房号今天在播、明天可能不在）进仓库就得有人维护它「是否仍然在播」，可它的价值恰恰不依赖这个。

> **所以这一节的可用形态只剩一种：房间号 → `current_qn` 的逐行记录（两张表都在上面，各自可复核），加一句"换个抽样源就换一批房间"。** `9/12` 这个数本身也撤掉了——不是算错，是**它只要能脱离这张表被引用，就已经在冒充分布**。**三个比率并列也不行**：并列听起来像"现象"，但每一个都能被单独摘出来当成"绝大多数"的凭据。**能并列的是集合（`交集 = 0`），不能并列的是比率。**

**能站住的说法只有一句**：签发哪一档由**房间与推流端**决定，**登录态不是决定因素**。

**两个方向都禁止**：任何数出来的比例都不许写成"绝大多数房间匿名就有原画"（连那个分数本身也别留着，它一脱离这张表就在冒充分布）；"未登录 = 压到 250"更不许写。**两个方向都是把一个样本当成一条规则**。这个项目在斗鱼体积门限上已经犯过一次（两个样本的中间值成了 `4000`），这里是第二次——两次的形状一模一样：**样本给了一个数，叙述把它升级成了一条规则**。

**两条限定，别当成更多证据**：
1. room 21452505 今天 `live_status=0`，拿不到响应，所以上面那张两房间对照里的 `[250]` 我无法复算，先留着但标为不可复现。
2. **只证明平台把 `current_qn` 标成 10000，没有解码验证画面真的是 1080P。** 要坐实得读流内的 SPS/分辨率，那是另一件事。

决策侧（价值主张、凭据形态、存储、降级、扫码交互）在 `架构.md` §8.2 / ADR-016。这里只留实测，不重复结论。

## 2. 斗鱼

| 用途 | 接口 | 实测 |
|---|---|---|
| 取流 | `POST /lapi/live/hlsH5Preview/{rid}` | 200，`data.rtmp_url` + `data.rtmp_live` |
| 首页 / 分类 | `GET www.douyu.com/gapi/rkc/directory/{cid1}_{cid2}/{page}` | 200，`data.rl[120]` |

Base：`https://playweb.douyucdn.cn`（取流）/ `https://www.douyu.com`（列表）。

### 2.1 取流：只需要一个 md5

请求头：
```
rid:  {rid}
time: {当前毫秒时间戳}
auth: md5(rid + time)          ← 小写十六进制，就是 rid 和时间戳直接拼起来做 md5
Referer: https://www.douyu.com/
```
请求体（form）：`rid={rid}&did=10000000000000000000000000001501`

播放地址 = `data.rtmp_url + "/" + data.rtmp_live`。虽然叫 rtmp_url，实际给的是 http(s) 的 flv/hls，交给 ExoPlayer 直接播。

> 这一条是整个项目里最省事的发现：**不用啃斗鱼的签名 JS**。`../../docs/逆向分析.md` 里记的那套 `ub98484234` + `v=2201202011` 现在完全不需要。

### 2.2 列表：一个接口覆盖首页和所有分类

`gapi/rkc/directory/0_0/1` → 全站 120 条
`gapi/rkc/directory/2_1/1` → 英雄联盟（`cid1=2` 是网游，`cid2=1` 是 LOL）120 条

字段：

| 字段 | 含义 | 映射到 `Room` |
|---|---|---|
| `rid` | 房间号 | `roomId` |
| `rn` | 房间标题 | `title` |
| `nn` | 主播昵称 | `hostName` |
| `ol` | 人气（整数） | `viewers` |
| `rs16` | 封面（1366 宽） | `coverUrl` |
| `c2name` | 分区名 | `areaName` |
| `av` | 头像相对路径 | 头像是 `https://apic.douyucdn.cn/upload/{av}.jpg_big.jpg` |

`rs16` 有些是 `.avif` 后缀。Coil 2.7 在 Android 上能不能解 avif 取决于系统解码器——**解析失败要有兜底**（`error` 占位图），别让它把卡片撑成空白。

### 2.3 FLV 那条路已经不能用了

拿 `rtmp_live` 里的 key 去拼 `https://vplay1a.douyucdn.cn/live/{key}.flv?uuid=`：实测**全部 TLS 握手中断**（`UNEXPECTED_EOF`），试过 http、`vplay1` 域名、加 token 都一样。所以首版只交付 **HLS 预览流**（1 条），**不要为了「多给几条线路」去拼 FLV**——那只会让播放器多一点一次就失败的机会。

代价：斗鱼只有「预览画质」一档，拿不到多清晰度。想要多档得回到签名路线（`../../docs/逆向分析.md`），首版不做。

### 2.4 「房间不存在」是 HTTP 200 + HTML，不是 404（2026-10-29 实测）

`GET https://www.douyu.com/betard/{rid}`，同一台机、同一 UA / Referer：

| `rid` | HTTP | `content-type` | 字节 | 正文 |
|---|---|---|---|---|
| `288016`（真实房间） | 200 | `application/json;charset=UTF-8` | 119584 | 正常数据 |
| `9999`（真实房间） | 200 | `application/json;charset=UTF-8` | 127820 | 正常数据 |
| `1` / `88888888` / `999999999` | **200** | **`text/html`** | **1354** | `该房间目前没有开放` |
| `0` | **200** | **`text/html`** | **1349** | `没有找到该房间` |
| `-1` | **200** | **`text/html`** | **5239** | 通用 404 页（`mod_404`），**复用同一张 `提示信息` 模板** |
| `abc` | **403** | `text/html` | 238 | Tengine 拦截页，到不了形状判据（`Net` 已归 `SIGN_INVALID` / `RATE_LIMITED`） |

**字节数以 `wc -c` 为准。** 同一份响应 `curl -w '%{size_download}'` 给 `1355`、`wc -c` 给 `1354`，差的那一个字节是 `$(…)` 吃掉的末尾换行。**一份记录里出现两个数，先怀疑量法，再怀疑记录**——这次是我先怀疑了记录，白花半小时。

六行里有五行的 `HTTP` 是 `200`，包括不存在的房间。**所以「房间不存在」不能靠状态码判**。剩下的候选是「响应体形状」，而形状里最顺手的那个维度——体积——是错的，见下。

#### 体积门限不成立（这一条推翻了我自己上一版）

上一版写的是「非 JSON 且 `< 4000` 字节 = 房间不存在」。这个门限**能通过当时所有样本**，因为当时手里只有两个点：错误页 1355、正常 JSON 119588。**两个样本的中间值是猜的，不是测的**，而 4000 这个整数让它看起来很像是测出来的。

把 `rid` 铺开以后，体积是连续分布的：**238 / 1349 / 1354 / 5239 / 119584 / 127820**。`< 4000` 那条线实际竖在 1354 和 5239 之间，两个方向各有一个反例，**都已经写成单测**：

| 输入 | 旧判据 | 后果 |
|---|---|---|
| 300 字节、`HTTP 200` 的风控页 | `ROOM_NOT_FOUND`（`report = false`） | **斗鱼整站静默失效**：每个房间都显示「房间不存在」，诊断页一声不响。这正是这套判据本身要防的那件事 |
| 「房间不存在」错误页哪天变胖到 200KB | `PARSE_BROKEN` | 把「用户输错」说成「我们坏了」：`report = true`，我们会把一个用户问题当线上故障去查 |

所以删掉它的理由不是「4000 不够精确」，是**它不成立**。「再调调门限」是错的方向：任何一个字节数都只是把一个连续分布切成两半，而这两半里都同时住着「房间不存在」和「不是房间不存在」。

#### 现在的判据：平台自己写在页面里的那句话

```kotlin
private val BETARD_ABSENT_MARKERS = listOf("该房间目前没有开放", "没有找到该房间")
```

两句都实测过，而且**不是同一句**：`betard/1`、`/88888888`、`/999999999` 是「该房间目前没有开放」，`betard/0` 是「没有找到该房间」。在平台那儿它们是一回事（这个号没有可展示的房间），所以映射同一个码。`detail` 现在是这串：`斗鱼：房间 X 不存在（命中斗鱼提示页「该房间目前没有开放 / 没有找到该房间」）bytes=1354 chars=1089`。**两个候选都写进去，不区分是哪一句命中的**——它们映射同一个码，不影响归责，只是诊断页少一句线索；要区分，就得让 `betardShape` 把命中的那串带出来，而不是再匹配一遍。

代码落点两处，都在 `DouyuSite.kt` 底部：

- `betardShape(body): BetardShape` —— **纯函数**，不碰网络，单测直接喂字节。四个成员：`JSON` / `NOT_FOUND_PAGE` / `OTHER_HTML` / `EMPTY`。
- `betardFailure(shape, url, roomId, body): SiteException` —— 形状 → 异常。`when` **穷尽 4 个成员**，`JSON` 那一支写 `error("…")`，**不写 `else`**。

| 响应形状 | 判成 | 为什么 |
|---|---|---|
| 空体 / 纯空白 | `PARSE_BROKEN` | 网关给了个空响应，不是用户输错 |
| 去掉 BOM 后 `{` 开头 | 正常，交给 JSON 解析 | 解析失败另算 `PARSE_BROKEN`（截断 / 改版） |
| 含 absent 标记串 | `ROOM_NOT_FOUND`（`report = false`） | 平台自己说的，可以照抄 |
| 其余非 JSON | `PARSE_BROKEN` | 改版 / 维护 / 风控 / 劫持，都归「我们读不懂」 |

**`betardFailureKind()` 已经删了**，它返回 `SiteError?`，用 `null` 兼职表达「解析成功」。Kotlin 只在 `when` **有值**时才要求穷尽，当语句用时靠的是 `SiteError` 那 13 个成员——于是漏掉的码被 `else` 一兜，就静默归进「成功」那一侧。换成 4 成员的字面量枚举之后，「成功」变成一个**必须显式写出来**的分支；将来给 `BetardShape` 加成员，`betardFailure` 会**编译报错**。`SiteError?` 那版做不到这一点，这正是这次返工的根。

#### 一个必须记下来的坑：模板名不是判据

**不能只匹配 `<title>提示信息 -斗鱼</title>`。** `betard/-1` 那张 5239 字节的通用 404 页（`mod_404`）**用的是同一张 `提示信息` 模板**，只配标题就会把「路径或域名写错了」说成「房间没了」。

这条比体积门限更隐蔽，因为模板名看起来「就是斗鱼的错误页特征」——它是从真样本里摘出来的、读起来无可挑剔，只是**顺带命中了一段我们不想要的东西**。判据要锚在**只有那件事才会出现**的字符串上（正文里那句话），不要锚在「这类页面通常长什么样」上。

#### 责任方向：歧义一律往「怪我们」那边倒

这和抖音是**同一条原则的两面**：抖音「页面里配不出 room_id」选 `PARSE_BROKEN`（宁可误报），斗鱼这里原来选的是漏报。统一后的规矩：**红一次查 15 分钟，漏一次整条通道无声失效**。

这条**差点被写反三次，是同一个坑换了三张脸**：更早的注释说「房间不存在是 404」，照它推会得出「`Net` 里 404 → `ROOM_NOT_FOUND`」；随后改成「解析失败就是不存在」；再改成「非 JSON 且体积够小就是不存在」。三种错法都把「平台改版」说成「房间没了」，区别只是靠 HTTP 码、靠 catch 兜底、还是靠一个字节数。**每一次都有一个可执行的判据，而且都能通过当时的样本**——这才是它反复回来的原因，而不是谁不认真。

**判据要能自证**：`detail` 里写全诊断信息，误判时不用再猜一遍。

#### `detail` 现在写 `bytes=N chars=M`

`Net.getBody()` 返回 `NetBody(text, bytes)`，`Net.get()` 委托它（`String` 兼容的旧签名还在）。`detail` 拼的是 `NetBody.size`：

```text
斗鱼：betard 返回了 HTML 而不是数据，且不是房间不存在的提示页（改版/维护/风控/劫持？）bytes=5239 chars=1089
```

**为什么要两个数**：`String.length` 是 UTF-16 字符数，不是字节数。一张 1354 字节的中文错误页，`length` 只有 1089 左右——拿它当体积判据、又在 `detail` 里写成 `bytes=`，就是给下一个人一把单位错的尺子，他 `curl -s … | wc -c` 对不上，就会怀疑记录本身错了（也就是本文开头那半个小时的同一个陷阱）。全仓 `bytes=${text.length}` 这种写法现在是 **0 命中**：要么按字节（`NetBody.bytes`），要么老实用 `chars=` 说清是字符数，不允许含糊。

顺带：这也解释了为什么斗鱼的失败分类里，只有 `betard` 这一处能判「房间不存在」，而 `playUrls` 那条路要靠业务字段 `error=102`（见 §2.1）。

## 3. 虎牙

| 用途 | 接口 | 实测 |
|---|---|---|
| 首页 / 分类 | `GET www.huya.com/cache.php?m=LiveList&do=getLiveListByPage&tagAll={0\|1}&page={n}` | 200，`data.datas[120]` |
| 取流 | `GET mp.huya.com/cache.php?m=Live&do=profileRoom&roomid={rid}&showSecret=1` | 200，`data.stream.baseSteamInfoList[0].sFlvAntiCode` |

### 3.1 anti-code 不用自己算

各家教程里最麻烦的就是虎牙的 `wsSecret`（`fm` + `wsTime` + `seqid` + `ctype` 拼串再 md5）。`showSecret=1` 会直接把算好的结果放在 `sFlvAntiCode` 里：

```
播放地址 = sFlvUrl + "/" + sStreamName + "." + sFlvUrlSuffix + "?" + sFlvAntiCode
```

实测 HTTP 200，拿到 531,999 字节的第一段（可以直接喂 ExoPlayer）。headers 带 `User-Agent`（桌面）+ `Referer: https://www.huya.com/`。

`baseSteamInfoList` 里通常有多条（`sCdnType` 分别为 AL / TX / HW / WS），**这就是播放页的线路列表**，按 `iIsMaster` 排序，主线路优先。

### 3.2 列表字段

| 字段 | 含义 | 映射到 `Room` |
|---|---|---|
| `profileRoom` | 房间号（**用它，不是 `privateHost`**） | `roomId` |
| `roomName` | 标题，**经常是空串** | `title` |
| `introduction` | 简介（如「银川」） | `roomName` 为空时的兜底 |
| `nick` | 主播昵称 | `hostName` |
| `totalCount` / `aliveNum` | 人气（字符串数字） | `viewers` |
| `screenshot` | 封面，**是 http 不是 https** | `coverUrl` |
| `gameFullName` | 分区名 | `areaName` |

两个必须处理的脏数据：

1. `roomName` 空串很常见（实测 `datas[0]` 就是空）。兜底顺序：`roomName` → `introduction` → `"{nick} 的直播"`。**不要显示空白标题**。
2. `screenshot` 走 http。这就是 `usesCleartextTraffic` 不能关的直接原因之一（另一个是斗鱼的 hdl 流）。

分类：`tagAll=1&tagName={urlencode 分区名}&page=1`。分区名用 `gameFullName` 里的中文（如 `英雄联盟`、`户外`、`王者荣耀`）。

### 3.3 两个线路坑（都会直接变成用户的黑屏）

**坑一：HLS 只有 HS 系 CDN 真的出流，AL / TX 的 `.m3u8` 恒 403。**（2026-10-29 实测，跨 4 个房间复验）

`baseSteamInfoList` 里每条都有 `sFlvUrl` 和 `sHlsUrl`，但实测（跨 4 个房间复验）：

| `sCdnType` | FLV | HLS |
|---|---|---|
| `AL` / `TX` | 200，或 302 跳转后 200 | **403** |
| `AL13` / `TX15` | 200 / 302 | **403** |
| `HS` / `HS24` | 200（个别房间 403，随房间变） | **200 / 206，真 m3u8** |

所以取值规则是：**FLV 保留全部 CDN，HLS 只保留 `sCdnType` 以 `HS` 开头的**。

这不是「优化」，是防止最伤人的失败模式：如果把 AL/TX 的 HLS 也塞进线路列表，用户按「换线路」会连吃两次黑屏——线路存在、状态码 403、播放器只能一路换下去，最后什么都没放出来。`core/site/HuyaSite.kt` 里按 `sCdnType.startsWith("HS")` 过滤，改之前先看这张表。

**坑二：`mp.huya.com` 的 `profileRoom` 会间歇返回 nginx 404。**（2026-10-29 实测）

同一个 URL 隔几秒再拉就是 200（桌面 UA、移动 UA 都复现过），body 只有 564 字节的 nginx 错误页。这不是风控、不是房间不存在——房间真不存在时返回的是 **HTTP 200 + `status:422`**。

处理方式：非 2xx 时**重试一次**再报错，异常信息带上原始 message。把网络抖动翻译成「房间不存在」是典型的假信息，宁可多花一次请求（约 150ms）。

> 上面两条坑 + 抖音 HLS 的 404 抖动，合起来才是完整的失败分类口径：**无响应 → 3s 提示 / 4s 真切（两段式）；404 → 原样重试一次（约 300ms）再判；403 → 不原地重试**（403 是签名/线路层面的拒绝，原地重试只会白撞）。这条规则的准确定义在 ADR 里，§3.3 只提供实测依据。

## 4. 抖音（**可用**：详情 + 取流全通，代价是两次请求）

| 用途 | 接口 | 实测 |
|---|---|---|
| web_rid → 19 位 room_id | `GET live.douyin.com/{web_rid}` 页面内嵌 JSON | 200，`"roomId":"…","web_rid":"…"` 严格配对 |
| 详情 + 取流 | `GET webcast.amemv.com/webcast/room/reflow/info/?type_id=0&live_id=1&room_id={19位}&app_id=1128` | 200，`status_code:0`，`data.room` + `data.room.stream_url` |
| 列表 / 分区 / 搜索 | `live.douyin.com/webcast/room/web/enter/`、`aweme/v1/web/live/search` | 需 `a_bogus`，未签名 2483「请先登录」/ 444 |

### 4.1 `reflow` 的参数必须 19 位 `room_id`（但用户输入可以是 4–12 位 `web_rid`）

这是曾经的错判来源，单独写清楚：

- `reflow/info` 的 `room_id` **只认 19 位内部 ID**。传直播间地址里那串 6–12 位的 `web_rid`，返回的是
  **HTTP 200 + `{"data":{"message":"Request params error"}}`**（`status_code` 10011；早期记录里写的是 4001038，**本次未复现**，见下条——两者是同一个响应，以 10011 为准）。
- 所以「HTTP 200 不构成成功证明」这条坑**保留**——它正是上面这个错判的现场。断言必须匹配 `"room":` 或 `"status_code":0`，只匹配 `"data"` 会误判成成功。
- 结论修正：抖音**不是「接口不可用」**，是「要两次请求」。这两次请求都是免签的，一次都不需要 `a_bogus`。
- **`10011` 这个码不是「房间不存在」的专属码（2026-10-29 取证）**。拿不存在的 19 位号去打，返回和「位数不对」**一字不差**：

  ```
  GET …/reflow/info/?room_id=1234567890123456789
  {"data":{"message":"Request params error","prompts":"Request params error\t"},"extra":{…},"status_code":10011}
  GET …/reflow/info/?room_id=773103753553            ← 12 位 web_rid，位数不对
  {"data":{"message":"Request params error","prompts":"Request params error\t"},"extra":{…},"status_code":10011}
  ```

  所以「房间不存在」和「参数不对」**在响应上区分不出来**，只有一个笼统的 `Request params error`。

  落到错误码时的判据（2026-10-29 定稿，改动过两版，下面是最终版）：

  - **`10011` 裸映射 `ROOM_NOT_FOUND`，不加任何前缀条件。** 理由不在「响应长什么样」，在**入参由守卫保证**：能进 `reflow` 的 id 一定是 19 位纯数字（`isDouyinRoomId`），所以「参数不合法」这一种解释在那个位置物理上不存在，`10011` 只剩「这个号没了」。
  - ⚠️ **曾经写在这里的判据已被推翻两次，别抄回去**：①“只有 `room_id` 由页面严格配对得出之后才够格判这个码”——用户**收藏/最近观看**的 19 位号是直接 return 的，从不过页面配对，前缀恒为 false，于是最常见的那条失败路径永远进不了这个码，一个必须显眼的码变成几乎不可达；②“位数不足也算房间不存在”——真相是守卫放得太松（`>= 15`），让 15–18 位打到了 `reflow`。
  - 陌生业务码一律 `PARSE_BROKEN`（我们没看懂）。协议真变时回来的码几乎不可能恰好还是 `10011`，所以裸映射自己会红。

  **入参形状规则**（`DouyinSite.resolveRoomId`，唯一实现是 `douyinIdShape()`，别在别处再写一遍数字）：

| 输入（纯数字） | 判定 | 发几次请求 | 失败归哪个码 |
|---|---|---|---|
| 19 位 | `room_id`，`reflow` 直接认 | 1（`reflow`） | `ROOM_NOT_FOUND`（10011 裸映射） |
| **4–12 位** | **`web_rid`**，必须去页面换 19 位 | 1（页面）+ 1（`reflow`） | 页面配不上 → `ID_UNRESOLVED` |
| 13–18 位 / `<4` / `>19` | 既不是 `room_id` 也不是 `web_rid` | **0（一个字节都不发）** | `ID_UNRESOLVED` |
| 非纯数字（`v.douyin.com` 的字母短码） | 未知形态，交给落地页 302 后配对 | 1（页面） | 配不上 → `ID_UNRESOLVED` |

  第二行是**最容易写错、也最容易“优化”掉的一行**：`web_rid` 实测有 **4 位**的（分享文案里那种短号，页面里照样能配对出 19 位 `room_id`），它是抖音在主界面上**唯一的常规入口形态**。把守卫写成「不是 19 位就抛」会让整个抖音入口在 UI 上变成「房间号位数不对」——编译通过、单测（如果只测 19 位和空串）也通过。
  第三行的意义是：位数不对**不许打到 `reflow`**，否则服务端回 `10011`，用户看到的是「房间不存在」，而那是**我们的输入校验缺位被说成了平台的结论**，还白耗一次风控额度。

### 4.2 web_rid → room_id 只能靠页面严格配对

```
GET https://live.douyin.com/{web_rid}     # 桌面 UA + Referer: https://live.douyin.com/
→ 页面内嵌 JSON（引号被转义成 \" ，先 replace("\\\"", "\"") 再匹配）
→ Regex: "roomId":"(\d{10,25})","web_rid":"(\d+)"    ← 必须配对，不能取页面里第一个 19 位数
```

**为什么不能取第一个 19 位数**：页面里混着大量推荐位、作品、专题卡的 id（实测某个直播间页里有 78 个 19 位数字，其中 77 个不是 room_id）。取错就是**给用户放另一个人家的直播**，而且不会报错——比失败更糟。

兜底**不是「往前找最近的 `roomId`」**，而是只认两种**相邻**顺序：

```
"roomId":"19位","web_rid":"输入"      ← 当前页面就是这个顺序
"web_rid":"输入","roomId":"19位"      ← 字段翻序也命中
```

理由有两层，都实测过：

1. 「往前找最近的那个」没有任何保证是这一个房间的——页面上 77/78 个 19 位数字不是 room_id，配错就是**放别人家的直播且一声不响**，比失败更糟。
2. 早先那版用 `"${html%%PATTERN*}"` 取前文，一旦页面里**根本没有这个 `web_rid`**（房间注销、短链失效落到首页），模板会把整页返回，于是「最近的那个」退化成「整页最后一个 `roomId`」——**房间不存在也能配出一个号**。同一个写法在 900KB 的页面上还会让 bash 卡死（实测 >12 秒无返回）。所以这条路整条删掉。

两种相邻顺序都不中 → 报错，不猜。哨兵脚本和 `DouyinSite` 是同一套判据（改一处必须改另一处，否则脚本会假绿）。

**`detail()` 返回的 `Room.roomId` 是 19 位的 `room.id_str`，不是用户输入的原样。** 另外三家返回的也都是平台真实 id（哔哩短号 `6` → `7734200`、虎牙 `profileRoom`、斗鱼 `rid`），抖音不能做唯一的例外：同一个房间否则会有两个 key（收藏、最近观看会对不上），而且弹幕以后要用 19 位 id，直接从 `detail` 里取就行，不必再反查一次页面。

`v.douyin.com` 短链：**能识别、失败可诊断、但不承诺可用**。实测失效短链 `302 → www.douyin.com`，落地页 **HTTP 200 且一个 `roomId` 都没有**——这是最坏的失败形态（看着成功），和 §4.1 那个「200 但是 Request params error」是同一类陷阱。

所以短链跳转后必须**恰好命中一个** `roomId`+`web_rid` 配对，否则**不许退化成「随便找个 19 位数字」**——那不是兜底，是随机抓人，而且抓错了不报错、直接放别人家的直播。

对外文案（产品口径，已定）：**「无法从这条链接定位直播间，请改用 live.douyin.com/房间号 或 App 内的分享链接」**。里面不许出现「短链已失效」——用户不知道什么是短链，只给他明确的下一步。「能识别、不承诺可用」这个判断留在本文和代码注释里。

### 4.3 取流：8 条线路，FLV 优先、HLS 兜底

`data.room.stream_url`：

```
hls_pull_url_map: {"FULL_HD1": "...", "HD1": "...", "SD2": "...", "SD1": "..."}
flv_pull_url:     {"FULL_HD1": "...flv", "HD1": "...", ...}
resolution_name:  {"FULL_HD1":"蓝光","HD1":"超清","SD2":"高清","SD1":"标清","ORIGION":"原画"}
```

- 地址是 **http**，全部要升 https（Android 9+ 默认禁明文）。
- `resolution_name` 里有「原画（ORIGION）」，但匿名用户常常**拿不到** `ORIGION` 的地址；清晰度列表要按 `hls_pull_url_map` / `flv_pull_url` 里**实际存在的 key** 生成，别照 `resolution_name` 抄。
- 实测（`web_rid=715855351148` → `room_id=7701975308739611407`）：FLV 3/4 是 200 `video/x-flv`（帧头 `464c5601`），HLS 4/4 是 206 `application/vnd.apple.mpegurl`。
- **douyincdn 的 m3u8 会间歇 404**（2026-10-29 实测）：同一个 URL 连拉 3 次可能前两次 404、第三次 206（`--http1.1` 与 `--http2` 都复现，所以不是协议问题），FLV 稳定。所以**顺序是 FLV 优先**；但 **HLS 必须留在列表里**（tvOS 的 AVPlayer 只吃 HLS，见 ADR-007），播放器遇到 HLS 404 要**先原样重试一次**再判换线路。「排在后面」和「不在列表里」是两件事——删掉 HLS 等于把 tvOS 的路封死。

### 4.4 列表 / 分区 / 搜索仍返回空（诚实失败）

这三项要 `a_bogus`（算法在 `webmssdk.js`，未登录还直接 2483「请先登录，再继续搜索吧」）。

- 首版 `DouyinSite` 的 `recommend` / `categories` / `categoryRooms` / `search` **返回空列表**，同时在 `LiveSite.capabilities` 里把对应位声明成 `false`——**空列表 + `true` 是欺骗**，UI 会读能力位显示「暂不支持列表」而不是「0 个房间」。
- 签名（WebView / QuickJS）**只对这三项有意义**，对 `detail` / `playUrls` **不需要**，这两项的能力位保持 `true`。

### 4.5 弹幕不可用：证据只有一条，别拿 `Request params error` 当理由

**加一句防误读**：§4.1 那个 `Request params error`（`status_code` 现测为 `10011`，早期记录写作 `4001038`）**不是弹幕不可用的证据**。它从头到尾只是 `room_id` 位数不对（web_rid 直接传给 reflow）。把它写成弹幕的原因，会让人以为「去修一下参数就能出弹幕」，白跑一趟。

弹幕不可用的**唯一证据**是握手本身：

```
wss://webcast100-ws-web-lq.douyin.com/webcast/im/push/v2/...      （及备用域）
signature=""          → HTTP/1.1 200 OK     ← 不是 101，握手根本没建立
完全不带 signature    → HTTP/1.1 200 OK     ← 同上
```

WebSocket 握手成功必须是 `101 Switching Protocols`。服务端回 **200** 说明它在 HTTP 层就把连接当普通请求处理掉了。而 `signature` 要 `frontierSign` 换 `X-Bogus`，v1 不做，所以：

- `capabilities.danmaku = false`，`DouyinDanmaku.stream()` 只 emit 一条 `Failed`；
- 与房间信息能否取到**完全无关**——`detail` / `playUrls` 全通的同时，弹幕就是连不上；
- 播放页据能力位整个不渲染弹幕层。**有意的**：给用户一个点了永远没反应的弹幕开关，比没有这个开关更差。

等签名器接通时，要同时动两处：`DouyinSite.capabilities.danmaku = true` 与 `DouyinDanmaku.stream()` 换实现。顺序上先换实现再翻位（翻早了只会让用户看到一个立刻失败的开关）。

> **补记（2026-10-29，senior spike）：上面这段的结论要收窄成「无签名不可用」，不是「抖音弹幕不可用」。** 独立 spike（`android/tools/douyin-danmaku-spike/`，不读 `app/src`）拿到了 **101** 并收到真弹幕：48 帧 / 46 msg / `ack 46` / 16 种 `method` / `WebcastChatMessage×3`（首条「如初见～：家人们左上角点点关注加个粉丝灯牌…」），复跑 60 帧 / 57 msg，两次 `exit 0`、0 条失败。
>
> 两个附带事实，都会改实现：
>
> - **引擎差异是决定性的，不是玄学**：同一 md5、同一参数只换引擎——Rhino 6 种组合（3 域名 × 编码/原样）**全 200**，V8 第一发 **101**；给 node 补齐浏览器 shim 仍 101，把 Rhino 的 signature 交给独立握手探针仍 200。**Rhino 签出的 16 位 signature 看起来完全正常，服务端就是不认**——所以「签名器可不可用」的唯一判据是 `101`，不是"签出来的串对不对"。**这一格是已否决项，不是待选方案**：`org.mozilla:rhino:1.7.14` 留在 spike 里只当**对照组**（同一份 `sign.js` 的第二台执行器），删掉它对照就没了；**别把它写进生产依赖**。证据全文在 `android/tools/douyin-danmaku-spike/README.md`（「结论」一节 + 文末那段 `probe.js`）。
>   **别把它写成「Rhino 不可靠」或「换个 JS 引擎再试一遍」**——那会把人引到错误方向。两条排除法排掉的是别的原因：① 给 node 补齐与 Kotlin `JsEngine.bootstrap()` 一致的浏览器 shim，**仍 101**，说明不是"缺个 API"；② 把 Rhino 算出的 signature 交给一份**不签名、不读 `sign.js`** 的独立探针，**仍 200**，说明**那串值本身就是错的**，不是握手流程写错了。于是只剩一个变量：**同一份 `sign.js` 在不同执行环境里算出了不同的值。** 方向是"换执行环境"（WebView/V8），不是"改签名算法"，也不是"换个引擎碰运气"。
>   **顺带一个做对了的地方，正好是本文 §1.3.1 的反面**：第二条排除法用的握手探针本来只活在 `/tmp`，写 README 时把全文抄了进去，**入参就是别人算好的 signature，不签名、不读 `sign.js`，谁都能复跑**。§1.3.1 撤掉的那个 `/tmp/qn_r3.txt` 是"会继续存在、却指到空处的坐标"；这里是同一个问题的另一种处理：**能抄进仓库的就抄进去，抄不进去的就说"没留下"，不留指针。**
> - `user_unique_id` **不必来自房间页**（随机 19 位照样 101）；房间页会被限流成 6KB 的「验证码中间页」，于是加了「首页 cookie + 自造 uid」的回退，并打印这次走了哪条路。
>
> 于是 `capabilities.danmaku = false` **今天仍然是对的**（客户端还没换实现），但它挡的已经不是"平台不给"，而是"我们还没接引擎"。

**「这个房间有没有弹幕」不能用 `user_count` / 在线人数判（2026-10-29 实测）。** 分类页里大量房间是门店、循环播放、无人值守直播：**人气高不等于有人说话**，按人数排序只能当候选顺序，最后仍要实测（证据在 `android/tools/douyin-danmaku-spike/README.md`「房间下播了怎么办」一节末尾，搜 `不能当「有没有弹幕」的判据`；同一份 README 记着这次跑通的那间是「真人在台上说话」的房）。

> **这一句原来写的是「实测某个几百人看的房间，整段会话里 `WebcastChatMessage` 只有 1 条，其余全是 `RoomDataSync` / `ResidentGuest` 这类系统帧」——那两个具体项都撤掉了。** 理由不是它们可疑，是**引文里没有它们**：`ResidentGuest` 全仓只有这一句提到（`grep -rn 'ResidentGuest' --include=*.kt --include=*.md .` → **1**，就是本文），README 里也**没有**「只有 1 条」这个读数（它只有一次 `ChatMessage×3` 的样本，和一句「空房间等再久也只有心跳和 `RoomDataSync`」）。**这比"数错了"更坏：引文本身是真的，只是它不包含那句话**——读者去核会核到一份真文档，然后找不到那一格，于是只能选择"相信作者记得"。结论不受影响（`user_count` 那条判据是 README 自己的实测结论），但**数字和字段名不能留在引文里充数**。

所以：

- `capabilities.danmaku` 是**平台级**能力位，**不按房间判**（按房间判会让 UI 对不同房间给出不同的能力表，那是第二份真相）；
- 真要判断"这个房间此刻有没有人说话"，判据只能是**会话内收到过多少条 `WebcastChatMessage`**，不是人气字段——**在这类房间里，「人气高」和「有人说话」是两件事**（同一次会话里两者可以一个很高、一个为零）。**但别把这句读成「两者不相关」**：这一轮没有做相关性测量，只说得出「人气不能代替弹幕」这一条——**没验过的相关性比没有相关性更贵**，写上去以后会被当成一条结论引用。
- 顺带一句：`room.user_count` 在本文里只承担「`viewers` 的映射来源」这一个职责（§5 总表），**别让它再承担第二个**。

### 4.6 下播房间的 `stream_url` 是「齐全但全死」（2026-10-29 实测）

这是写取流时最容易踩的一条，单列出来：

| `room_id` | `room.status` | `stream_url` | 实际拉流 |
|---|---|---|---|
| `7701975308739611407`（在播） | **2** | 4 路 FLV + 4 路 HLS | FLV 200 `video/x-flv`，HLS 206 |
| `7701710981495720704`（已下播） | **4** | **同样是 4 路 FLV + 4 路 HLS，一条不少** | FLV **404**（body 空），HLS **无响应（超时）** |

所以：

- **在播判据只有 `room.status`**：`2` 直播中、`4` 已下播。**不能拿「`stream_url` 存在」当 live 信号**——它会给你 8 条看起来完全正常的地址。用它判 live，下播房间会被显示成「直播中」，点进去是转圈到首帧超时，也就是最难查的那类「接口全通但用户看到黑屏」。
- `playUrls` 必须先判 `status` 再判 `stream_url`。不先拦下来，播放器拿到的是 8 条必然失败的地址，用户看到的是转圈而不是「已下播」这句人话。
- `detail` 的 `qualities` 在「拿不到线路」时必须是空列表，否则清晰度条上会出现 4 个按了必然失败的档位。
- 反过来，哨兵脚本**不该**断言 `"stream_url"`：下播房间照样有，它区分不出「接口挂了」和「房间下播」。断言 `"status_code":0` + `"room":` 存在才是「接口活着」的干净判据。

**判据是两层，不是一个 `&&`。** 代码里写成了两个变量（`DouyinSite.kt`，搜 `val live = status == 2` 与紧跟的 `val playable = live && stream != null && hasPullUrl(stream)`），别在下次重构时合并回去：

| 层 | 看什么 | 回答的问题 | 填到哪 |
|---|---|---|---|
| **态度** | `room.status == 2` | 平台说这个房间在不在播 | `Room.live` |
| **能力** | `hasPullUrl(stream_url)` | 平台有没有给出线路 | `qualities` + `playUrls` |

- **只信线路** → 下播房间满配 8 条地址，等于把这个 bug 原样复现。
- **只信 `status` 就宣称「能看」** → 会漏掉「标着在播但一条线都没给」的房间。
- **把两者合并成 `live = status == 2 && 有线路`** → 「`status == 2` 但结构解析失败」会被显示成**「未开播」**，等于**拿我们的故障冒充平台正常**：用户以为是主播没开，诊断页也留不下任何痕迹。这和我们在哨兵上否掉的「软失败」是同一个毛病。

所以 `Room.live` 只填态度（模型只有一个 bit，表达不了「在播但没线路」），能力缺失由 `playUrls` 抛一条**独立**的错：**「已开播，但取不到画面（接口可能改版）」**（产品口径，`detail` 里才写「`status==2` 但 `hasPullUrl` 为假」这种诊断细节）——和「已下播」/「未开播」是三句不同的话，点进去能分辨、日志能计数。代价是会出现「能点但播不了」的卡，但那本来就是真的。

**「在不在播」在本项目里不止一个判据**——弹幕层还有自己的一条通道。那件事的完整论述（三套判据各看什么字段、为什么现在不冲突、将来分歧以谁为准、由此派生的三条跨层规矩）**只在 `android/docs/架构.md` §3.2 里那段「三套"在播"判据不是同一个真相来源」写一遍**，本节不复述。同一个结论写两处，将来只有一处会被改。

**留一份本地证据，说明为什么这次要合并**：本节早前的版本在这里写过「虎牙两处都叫 `liveStatus`，一个是 `mp.huya.com` 的页面数据、一个是取流接口返回」。核实后是**同一个字段、同一个接口（`mp.huya.com/cache.php`）、只是两次不同的请求**——`Sites.detail()` 一次、`HuyaDanmaku.resolve()` 一次，中间隔着缓存层。两份文档当时说法不同，而**两边都读得通**，这正是重复叙述的代价：没人能判断哪个是真的。按 §3.2 为准。

### 4.7 前置闸门：别把恒定失败交给重试器

这一条是从上面那张表推出来的，比「记得判断下播」有用，因为「记得」是不传代的知识：

> **只有「同一个请求重发一次，可能得到不同结果」的失败，才进重试分类。下播房间的 404 是幂等的——再发一万次也是 404。凡幂等失败，必须在进重试器之前就被闸门拦掉。**

本质是：**在播和下播的响应形状完全一样**（4 FLV + 4 HLS，一条不少），只有 `status` 不同。所以播放器错的不是「重试策略」，是「它压根不该开始重试」——把一个恒定 404 交给为瞬时失败设计的重试器，等于让重试器在错误的对象上空转，用户看到的就是「转圈到首帧超时」。

四家各有自己的闸门字段，别只按 HTTP 状态码统一判：

| 平台 | 闸门字段 |
|---|---|
| 抖音 | `room.status == 2` |
| 哔哩 | `live_status`（1 直播 / 2 轮播） |
| 虎牙 | `liveStatus` / 8001 推送；房间不存在是 HTTP 200 + `status:422` |
| 斗鱼 | `ss` |

「前置闸门 + 三分类重试」这两层结构写在 ADR-007，本文只提供实测依据。

> **落地缺口（2026-10-29 核对）：这条规矩在弹幕层还没生效。** `SiteError.retryable` 全仓只有两处真读取——`core/site/HuyaSite.kt`（搜 `if (!e.kind.retryable || attempt == 1) break`）与 `ui/components/Bits.kt`（搜 `val showRetry = onRetry != null &&`）；`core/danmaku/` **0 处**。后果很具体：`prepare()` 抛的 `ROOM_NOT_FOUND`（`retryable = false`）照样被退避重试 5 次（1+2+4+8+16 = **31 秒**）才告诉用户房间号错了——**正是这一节禁止的"把恒定失败交给重试器"**，只不过发生在弹幕而不是播放器。
>
> 修法不是再补一个 `if`：弹幕层的重试器要读 `kind.retryable`，否则那张 13 码的表在弹幕这一侧只起到了"取值正确"的作用，没有起到"行为正确"的作用。

## 7. 回归流程

改完取流层 / 上线前：

```bash
cd android
./tools/run-unit-tests.sh       # 单测 38 条：13 码映射 + 抖音入参形状 + 斗鱼响应体形状 + 虎牙重试次数
./tools/error-mapping-check/run.sh   # 离线验收 31 条：不依赖 Gradle/Android，JDK 就能跑
./tools/probe-sites.sh          # 12 项应全 ok（抖音 2 项：页面配对 + reflow，均为硬断言）
./tools/tv-verify.sh            # 模拟器装机 + 按键走查 + 截图
```

三套脚本分工不同，**不是重复**：

| 脚本 | 需要什么 | 验的是什么 | 什么时候红 |
|---|---|---|---|
| `run-unit-tests.sh` | Gradle + JDK（首次要下 `mockwebserver`） | `Net` 的 13 行映射逐条断言 `kind` **和 `detail`**；抖音入参形状 10 条；虎牙重试**次数** | 我们把码映射写错、`catch` 落空、守卫放太松/太紧 |
| `error-mapping-check/run.sh` | 只要 JDK（用 `com.sun.net.httpserver` 真起服务端） | 同上，但不依赖 Gradle 与 Android SDK | 想在没有 Android 环境的机器上复核错误码 |
| `probe-sites.sh` | 能连公网 | **上游接口本身**还活着、字段没改 | 平台改版，不是我们的 bug |

前两个是「我们的逻辑对不对」，第三个是「世界有没有变」。**上游改了但映射没错时，只有第三个会红**——别把三种红当同一件事处理。

`probe-sites.sh` 非零退出说明有接口变了，输出里直接给出「哪家 / 哪个接口 / HTTP 码 / 响应片段」，按最后一节的提示对号入座即可。

抖音那一项**红的时候先看文案再动手**，脚本已经把两种原因分开写了：

| 输出 | 含义 | 该做什么 |
|---|---|---|
| `页面配对→room_id FAIL … 已不在页面上（换一个 DOUYIN_WEBRID）` | 主房间没了，备用房间还能配出号（reflow 那行会接着用备用号验，通常是 `ok`） | 换 `DOUYIN_WEBRID`，接口没坏 |
| `页面配对→room_id FAIL … 两个房间都配不上：抖音页面结构变了` | 免签换算通道可能已关 | 按 §4.2 重新抓页面确认，别猜 |

失败路径多打的那一次请求（备用房间）就是为了这条区分——抖音是四家里唯一没有兜底的平台，一声红必须直接指向下一步。

判定只有三种：`ok` / `跳过` / `FAIL`，**没有「软失败」**。「失败了但放过」是含糊通过，它让退出码失去意义，最后没人看结果。`SKIP_OK=1` 环境变量只为临时排查留口子，当前没有任何一项在用。合法的「跳过」只有一种：HTTP 成功 + 结构正确 + 只是房间当前不在直播（打印原因，不计通过也不计失败）。
